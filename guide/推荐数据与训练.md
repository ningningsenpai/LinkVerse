# LinkVerse 推荐数据与训练

## 数据来源

推荐训练支持两类入口，但一次训练只能选择一种数据来源：

| 数据来源 | 用途 | 数据标识 |
|---|---|---|
| 第二阶段 CSV | 迁移历史商品、用户画像和交互，用于复现实验与兼容验证 | `SYNTHETIC` |
| Trade 业务快照 | 由商品快照、业务事件和数据清单组成，用于第三阶段业务归因与训练 | `REAL` 或 `SYNTHETIC` |

`REAL`、`SYNTHETIC` 和脚本化验证数据分别统计，不在同一结论中混用。当前公开的推荐效果数据主要来自 `SYNTHETIC` 数据，因此只能说明离线方案改进，不能直接解释为线上点击率或成交率提升。

## 数据文件与字段

### 旧数据迁移结果

旧 CSV 经清洗后转换为 Parquet，形成以下数据集：

| 文件 | 关键字段 | 说明 |
|---|---|---|
| `items.parquet` | `listing_id`、`legacy_item_id`、标题、作者、描述、价格、类目、卖家、发布时间 | 清洗后的商品内容与属性 |
| `personas.parquet` | `user_key`、`legacy_user_id`、类目与关键词画像 | `user_key` 使用 HMAC 处理，避免把业务用户 ID 直接作为训练标识 |
| `interactions.parquet` | `user_key`、`listing_id`、`event_time`、`click`、`cart`、`forward`、`legacy_buy_signal` | 保留旧交互的二值信号；旧 `buy` 明确改名为兼容信号 |
| `item-id-mapping.parquet` | `legacy_item_id`、`listing_id` | 保证迁移前后商品可追溯 |
| `manifest.json` | Schema、来源、行数、哈希与生成时间 | 描述一次数据快照并用于完整性校验 |

迁移会移除 `rating`、`last3m` 等会直接泄露结果或含义不稳定的历史派生字段。模型只使用在预测时真实可获得的特征。

### Trade 快照

Trade 快照以 JSONL 与清单组合交付：

| 文件 | 主要内容 | 校验重点 |
|---|---|---|
| `objects.jsonl` | 商品和必要业务对象的时点状态 | 主键唯一、字段类型、状态合法 |
| `events.jsonl` | 曝光、详情、加购、下单、支付与退款事件 | 事件唯一、引用存在、时间合法 |
| `manifest.json` | 数据版本、来源、文件哈希和统计值 | 哈希一致、文件齐全、来源单一 |

加载器会拒绝重复主键、悬空引用、哈希不一致和来源混合的数据，校验通过后才转换为训练用 Parquet。

## 样本示例

下面展示 Trade 快照中的事件结构。ID 与时间为说明用示例，字段名与当前导出格式保持一致：

```json
{
  "event_id": "evt_01K...",
  "event_type": "PAYMENT_SUCCEEDED",
  "event_time": "2026-09-05T10:20:31Z",
  "ingested_at": "2026-09-05T10:20:32Z",
  "user_key": "5d7b...",
  "object_id": "1024",
  "request_id": "req_01K...",
  "session_id": "session_01K...",
  "recommendation_delivery_id": 30001,
  "position": 3,
  "source": "RECOMMENDATION",
  "model_version": "trade-ranker-20260908",
  "order_no": "LV202609050001",
  "refund_reason_code": null,
  "schema_version": 1,
  "data_source": "REAL"
}
```

- `event_id` 用于去重，同一业务事件只进入样本一次。
- `event_time` 决定时序切分，`ingested_at` 用于判断事件在训练时是否已经可见。
- `user_key` 是 HMAC 生成的稳定匿名标识，不用于反查业务账号。
- `recommendation_delivery_id` 与 `position` 用于判断行为是否由某次推荐投递产生。
- `source` 表示行为入口；`data_source` 表示数据事实来源。快照清单另行记录 `traffic_origin`，用于区分自然流量与脚本流量。

## 标签与负样本

业务事件通过固定增益表达用户意图强度：

| 事件 | 增益 | 含义 |
|---|---:|---|
| 曝光 | 0 | 只有在成熟窗口结束后仍无后续行为，才形成负反馈 |
| 查看详情 | 1 | 弱兴趣 |
| 加入购物车 | 3 | 中等购买意图 |
| 创建订单 | 7 | 强购买意图 |
| 支付成功 | 15 | 最强正反馈 |

用户主动退款可作为负偏好信号；系统因迟到支付补偿产生的退款属于交易恢复结果，不代表用户不喜欢商品，因此保持中性。曝光经过 **30 分钟成熟窗口** 后仍无点击、加购、下单或支付，才生成负样本，并额外保留 5 分钟缓冲以容纳迟到事件。

旧 CSV 的兼容训练使用 `click=1`、`cart=3`、`legacy_buy_signal=7`。新旧标签会通过来源和 Schema 区分，避免把历史 `buy` 直接解释成已完成支付。

## 时间切分与防泄漏

基础训练按事件时间使用 60%/15%/10%/15% 的窗口划分训练、校准、验证和测试数据。召回器、热门度统计、文本词表、用户画像和负样本只能读取对应训练时间窗，不能看到验证或测试窗口的后续行为。

训练前执行以下防泄漏检查：

1. 同一事件 ID 不跨数据集重复。
2. 用户与商品的历史特征只由当前样本时间以前的数据构建。
3. 召回索引和流行度统计不读取测试窗口。
4. 标签字段、支付结果和未来聚合值不能进入预测特征。
5. 数据来源、时间边界、随机种子和 Schema 写入实验记录。

## 候选组与特征

排序训练先通过与线上一致的召回和融合链路，为每个用户生成最多 **500** 个候选，再为候选计算特征。2026-09-08 未晋级候选使用的 v3 Schema 共 15 维：

| 特征名 | 字段含义 |
|---|---|
| `prior_popularity_count_ratio` | 当前请求时间以前的商品正反馈数，相对目录最大值的比例 |
| `category_affinity` | 用户历史与当前上下文对候选类目的偏好占比 |
| `author_affinity` | 用户历史与当前上下文对候选作者的偏好占比 |
| `price_distance` | 候选价格与用户历史价格中心在 `log1p` 空间中的距离 |
| `freshness` | 按 30 天时间尺度指数衰减的商品新鲜度 |
| `tower_similarity` | 用户向量与商品向量的内积相似度 |
| `known_user` | 用户是否存在于双塔用户词表 |
| `fusion_score` | 多路召回归一化加权后的 `recall_score` |
| `has_fusion_score` | 候选是否具有融合分，明确区分真实零分与补位缺失值 |
| `popular_reciprocal_rank` | 商品在热门通道中的倒数排名证据 |
| `source_two_tower` | 是否由双塔召回命中 |
| `source_item_cf` | 是否由 ItemCF 召回命中 |
| `source_tfidf` | 是否由内容 TF-IDF 召回命中 |
| `source_popularity` | 是否由热门召回命中 |
| `source_new` | 是否由新品召回命中 |

v2 的 5 维特征继续作为兼容基线；v3 在模型元数据中固定特征名称、顺序和版本。加载时只要维度或顺序不一致，在线服务就拒绝候选模型。

## 训练与模型包

训练过程依次完成数据校验、时间切分、召回拟合、候选构建、特征生成、LambdaRank 调参、固定测试集评估和模型打包。Optuna 只在训练与验证窗口选择超参数，最终测试窗口只用于一次冻结评估。

模型包至少记录：

- 数据清单与文件哈希；
- 代码版本、随机种子和训练配置；
- 召回索引、排序模型与特征 Schema；
- 离线指标、Bootstrap 区间和延迟结果；
- 模型版本、生成时间和兼容的服务版本。

在线发布与失败保留旧模型的流程见[推荐系统设计：模型发布与回滚](推荐系统设计.md#模型发布与回滚)。

## 指标口径

| 指标 | 计算含义 | 解读方式 |
|---|---|---|
| Recall@50 | 每个可评估用户在测试窗的正增益目标商品中，有多少进入前 50 个结果 | 衡量结果覆盖目标商品的能力；越高越好 |
| HitRate@20 | 每个可评估用户的前 20 个结果是否至少命中一个正增益目标 | 先逐用户记为 0 或 1，再取平均；越高越好 |
| NDCG@20 | 对前 20 个结果使用 `2^gain - 1` 的增益，并按 `log2(rank + 1)` 折损后除以理想 DCG | 同时衡量多级增益目标是否出现及其位置；越高越好 |
| Catalog Coverage@20 | 所有用户前 20 个结果触达的去重商品数，占共同可推荐目录的比例 | 衡量全局覆盖；下降可能意味着结果更集中 |
| P95 延迟 | 95% 请求在该时间以内完成 | 衡量尾部响应；必须结合候选数、并发和环境说明 |
| Bootstrap 区间 | 对用户组重采样得到指标差值区间 | 区间跨 0 时，不能断言改进具有稳定统计优势 |

训练候选组 `500`、接口请求 `candidate_count=100/300`、评估截断 `@20/@50` 是三种不同参数。报告指标时必须同时说明数据来源、基线版本、评估窗口、候选规模和服务负载，避免只展示百分比。

2026-09-08 比较固定 7,581 个测试用户，其中 7,541 人在公共目录和历史排除后仍有正增益目标，作为可评估用户。Recall、HitRate 和 NDCG 先逐用户计算，再对这 7,541 人做宏平均；没有有效正目标的用户记为 `null`，不进入三项质量指标的平均。Coverage 汇总全部 7,581 个测试用户的前 20 个结果，并以所有参与比较方案的 **6,262 个共同商品目录**为分母。这里的“目标商品”来自 `SYNTHETIC` 历史测试窗，不表示真实线上用户行为。
