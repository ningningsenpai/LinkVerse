# LinkVerse MVP 阶段 6：可靠性与可观测性执行设计

## 1. 目标与范围

阶段 6 不新增业务功能，只收口阶段 4～5 已存在的消息、补偿、对账和观测能力。目标是让重复、延迟、短暂依赖故障和毒消息都有可查询、可恢复且有上限的处理路径。

本阶段不引入 Kafka、Seata、Sentinel、Elasticsearch 或完整 Grafana/OTLP 部署。使用现有 RabbitMQ、MySQL、结构化日志和 Micrometer。

## 2. Outbox 与消费规则

- Relay 按 `next_attempt_at,id` 小批量抢占待发送记录，抢占有租约，进程崩溃后可重新领取。
- Publisher Confirm 成功后标记已发送；确认未知视为可重发，不宣称 exactly-once。
- 默认最多尝试五次，采用有界退避；超过上限或遇不可重试错误后发布到对应停车队列并保留原因摘要。
- 消费去重、业务更新和后续 Outbox 必须位于同一 MySQL 本地事务；提交后才 ACK。
- 人工重放必须按事件 ID 执行，先确认根因已修复；重放仍复用原事件 ID。

## 3. 对账能力

统一输出以下差异，不自动覆盖未知状态：

| 对账对象 | 主要差异 |
|---|---|
| 订单—支付 | 订单状态与 Payment 权威状态不一致、长期 `CLOSING` |
| 支付—退款 | 迟到成功无退款、退款长期 `UNKNOWN` |
| MySQL—Redis 库存 | 权威库存与稳定投影不一致 |
| 秒杀预约 | Redis 已预扣但无 MySQL 记录、预约长期中间态、订单缺少预约终态 |
| Outbox—RabbitMQ | 待发送过久、重试超限、停车消息未处理 |

对账脚本输出差异类型、业务标识、首次发现时间、建议动作和是否需要人工处理。

## 4. 日志与指标

结构化日志按实际链路携带 `service`、`request_id`、`trace_id`、`event_id`、`order_no`、`intent_no`、`reservation_no` 和 `error_code`。不存在的字段不输出空值；令牌、回调原文、HMAC 密钥和完整签名禁止写入日志。

Micrometer 至少记录：

- 下单、支付创建、回调、关单、退款和秒杀结果计数；
- Outbox 待发送数、最老消息年龄、重试数和停车数；
- 消费重复数、失败数和处理延迟；
- `CLOSING`、`UNKNOWN`、预约中间态和对账差异数；
- Redis/MySQL 库存差异。

## 5. 执行步骤

1. 将阶段 4 的最小 Relay 扩展为带租约、退避、停车和恢复的共享实现。
2. 为 Trade 与 Payment 统一事件查询、重放入口和队列命名。
3. 补齐订单、支付、退款、库存、预约和 Outbox 对账服务。
4. 增加 Micrometer 业务指标和跨 HTTP/MQ 的 MDC 关联字段。
5. 增加敏感信息扫描和错误摘要限制。
6. 通过依赖中断、重复消息和毒消息测试验证恢复路径。

## 6. 异常边界

- 未知状态必须保留占用并告警，禁止猜测成功、关闭或释放库存。
- 重试次数和退避时间均配置化但有安全默认值，不允许无限 `requeue`。
- 人工重放不能绕过消费者幂等键或数据库状态机。
- 指标和日志失败不得破坏核心交易事务；记录失败只能降级为受控告警。

## 7. 测试与验收门禁

- RabbitMQ 中断后恢复，Outbox 积压最终清零。
- 消费事务提交后 ACK 前中断，重投不产生重复副作用。
- 毒消息进入停车队列，不阻塞后续正常事件，修复后可按 ID 重放。
- 对账能够稳定发现构造的订单、支付、退款和库存差异，且不静默改写。
- 日志能够从请求关联到订单、支付和事件，敏感信息扫描为零命中。
- 指标端点包含规定业务指标且标签基数有界。
- 全量 Maven `clean verify` 通过后才允许提交本阶段。
