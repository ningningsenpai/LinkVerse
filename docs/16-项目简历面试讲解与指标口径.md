**三、第一版前端：怎样把“写页面”讲成业务能力**

这一部分的个人分工来自你的说明。当前仓库没有第一版前端源码，下面是回顾旧实现的准备提纲；不要把其中尚未核实的机制背成已经做过。

一个完整前端业务闭环，需要解释用户输入如何变成可确认的结果。例如交易页面应能说明：商品展示 → 登录和购买资格检查 → 提交 → 等待或失败 → 订单查询与结果展示。组件拆分、接口封装等技术选择应围绕这个过程讲。

| 面试问题 | 应回忆的具体细节 |
|---|---|
| 你“独立完成全部前端”具体包括什么？ | 页面清单、路由、组件、接口联调、表单校验、异常状态、最终演示；用第一版仓库和截图说明 |
| 如何避免重复点击下单？ | 前端按钮禁用和提交中状态只能减少误操作；重试、刷新和网络重发仍需后端幂等保证 |
| WebSocket 和 HTTP 如何分工？ | HTTP 适合查询与普通提交；WebSocket 用于持续推送。旧版是否做了重连、历史消息补拉和去重，应按旧代码回答 |
| 支付完成页面如何判断成功？ | 当前设计以服务端查询结果为准，浏览器跳转本身不构成支付事实；旧版是否同样实现需单独核实 |
| 前端权限检查够不够？ | 路由和按钮控制用于体验，后端仍须验证令牌、资源所有权及业务状态 |

口述时可以先说：“我独立完成页面和交互，还负责把登录、交易和聊天的接口联调成可演示闭环。”随后选一个你最熟悉的真实页面展开，不必罗列所有前端术语。

**四、微服务拆分：为什么拆、拆完多了什么成本**

拆分的主要价值是明确职责和数据所有权，使服务能独立修改、测试和部署。不能只凭拆成微服务就声称吞吐提升；远程调用、序列化、鉴权和网络失败反而会增加成本。

`Schema` 在这里指服务独占的数据库空间。Identity、Trade、Payment 可以在本地共享一个 MySQL 实例，但分别使用自己的 Schema 和账号。业务服务通过 API 或事件协作，不跨边界直接更新别人的业务表。

用户与服务身份的区别：

- 用户令牌回答“当前是谁、可以访问哪些自己的资源”。例如查询订单还要检查订单买家是否为当前用户。
- 服务令牌回答“哪个已授权服务在调用内部能力”。Trade 调用 Payment 或 Recommendation 时使用服务身份。
- JWT 是令牌格式，OAuth2 是授权协议，不能把二者混为同一个概念。
- `iss` 表示签发者，`aud` 表示目标受众，`exp` 表示过期时间，`scope` 表示授权范围。本项目还区分用户／服务用途等档案声明。
- 网关验证不能代替资源服务验证，否则绕过网关直连服务可能绕过安全边界。

“跨服务契约”要讲到字段和错误语义：Trade 创建支付时传入订单号、买家、商户、服务端金额、币种及过期时间；Payment 检查同一订单重复请求是否与原快照一致。超时后不能直接认为远端没执行，应利用幂等重试或权威查询恢复结果。

可以这样回答为什么单独拆 Payment：

> 订单关心购买资格和库存占用，支付关心金额、渠道通知及资金状态。我把两类事实分开，通过服务身份和事件契约协作；代价是跨服务不能依赖一个数据库事务，所以需要幂等、状态机、Outbox 和补偿。

**五、支付链路：先确定事实，再决定状态**

**5.1 普通下单的关键不变量**

“不变量”就是并发、重试和故障时也不能破坏的规则。本项目至少包括：库存不为负；同一用户同一幂等请求只创建一个订单；订单使用服务端金额；支付成功不能被超时任务随意覆盖。

普通订单当前是单商品、数量为 1 的接口，不能直接说已经实现通用多商品结算。

订单创建的实际做法：先校验请求、购买者与商品资格；按买家和幂等键查询已存在结果；未命中时进入事务写订单、条件扣库存、保存商品快照。库存不足时抛异常，整个事务回滚，不留下半个订单。

核心 SQL 的简化表达：

```sql
UPDATE sku_stock
SET available = available - 1,
    version = version + 1
WHERE listing_id = :listing_id
  AND available >= 1;
```

`listing_id` 是商品编号；`available` 是 MySQL 的权威可用库存；`version` 是版本计数；影响行数为 1 表示本次扣减成功，为 0 表示未满足条件。这里主要依赖库存条件更新，不能只因更新了 `version` 就说已经用 `WHERE version = old_version` 做乐观锁比较。

“先 SELECT 有库存，再无条件 UPDATE”把判断与扣减拆开，两个请求可能同时读到最后一件库存。条件更新把判断和扣减放进数据库的一次原子修改中。

**5.2 幂等键不是普通请求编号**

| 变量 | 含义与作用 |
|---|---|
| `Idempotency-Key` | 客户端为同一次购买意图提供的稳定键，当前限制为 8～64 个可见 ASCII 字符 |
| `buyer_id` | 买家身份，由认证上下文确定；不同买家不能共用一条订单幂等记录 |
| `request_fingerprint` | 对买家、商品和数量等语义字段计算摘要，判断同键是否被用于不同请求 |
| `order_no` | 已生成订单的业务编号 |
| `(buyer_id, idempotency_key)` 唯一约束 | 多实例并发下裁决重复创建，而不是仅靠内存判断 |

相同键、相同内容，返回原订单；相同键、不同商品或数量，拒绝复用。并发时即使两次查询都未命中，唯一约束仍能选出一个成功事务，失败方回滚后读取已提交结果。

**5.3 为什么保存订单快照**

假设下单时书价是 50 元，商家随后改成 60 元。订单和支付不能跟着商品现价改变。项目保存商品、卖家、标题、价格、币种等下单时字段，后续支付使用订单快照。金额使用 `BigDecimal`／数据库 `DECIMAL`；这与“前端显示两位小数”不是同一层面的保障。

**5.4 支付成功的正常路径**

```text
用户创建订单
  → Trade 保存订单与库存结果
  → Trade 使用服务身份调用 Payment，创建或复用 Payment Intent
  → 本地 Mock 渠道产生通知
  → Payment 验签、校验订单和金额、去重
  → Payment 本地事务更新支付状态并写 PaymentSucceeded Outbox
  → Relay 发布 RabbitMQ 事件
  → Trade 幂等消费，校验订单金额与币种，更新为 PAID
```

`Payment Intent` 是支付意图记录，包含“为哪笔订单付多少钱”等信息；存在 Intent 不代表已经付款。`intent_no`、`order_no`、`notification_id`、`provider_txn_no` 分别表示支付意图、订单、渠道通知、渠道交易流水，不能混用成一个唯一键。

回调先校验 HMAC 签名，再解析和核对通知中的订单号、商户、金额、币种及成功状态。通知 ID 与载荷摘要用于识别同通知重放和同通知改内容；数据库条件更新限制合法状态迁移。

**5.5 “100 次回调重放只迁移一次”如何得到**

测试先创建一个 Intent，构造一份合法签名通知，对同一内容连续调用回调处理逻辑 100 次，最后断言：回调记录为 1 条、成功 Outbox 事实为 1 条、Intent 为 `SUCCEEDED`。测试使用 Testcontainers 提供的真实 MySQL 与 Mock 渠道，不是连接真实支付商户。

这里“只迁移一次”指副作用仅发生一次。重复请求可以都返回成功，这向通知发送方表示结果已经被接收，并不要求把后续 99 次都报错。

**5.6 两类竞态分别在测什么**

| 场景 | 两个竞争操作 | 设计如何收敛 |
|---|---|---|
| 创建支付／关闭支付 | 创建 `PENDING` 与关闭同一订单的 Intent | 关闭先到且记录不存在时写 `CLOSED` 墓碑；创建不能把已关闭记录重新变为待支付。测试最终为 `CLOSED` |
| 支付成功／关闭支付 | `PENDING → SUCCEEDED` 与 `PENDING → CLOSED` | 条件更新裁决赢家；成功先到则保持成功，关闭先到后收到成功则进入退款补偿，测试最终为 `SUCCEEDED` 或 `REFUNDED` |

每轮使用新的订单，借助线程池和 `CountDownLatch` 让两个任务接近同时开始，等待任务结束后查数据库断言。每类循环 1000 轮。这是竞态集成测试，不是 1000 并发 HTTP 容量测试，也不是穷尽所有生产故障的数学证明。

Trade 超时关单还会先把到期订单认领为 `CLOSING`，调用 Payment 按支付权威状态裁决：已成功则结算为 `PAID`；已关闭或已退款则关闭订单并处理库存。调用失败时保留重试机会，不能单凭 HTTP 超时断言没有收到钱。

迟到成功的处理思路是：“已关闭订单不能重新打开占用库存；如果钱已经付了，走退款和可追溯的补偿记录。”当前退款是 Mock 实现；真实渠道超时、查单、退款未知状态还需要渠道适配和进一步验证。

**六、可靠消息与秒杀：把故障窗口讲出来**

**6.1 为什么需要 Outbox**

直接先提交 MySQL、再发 MQ，会存在数据库已成功但进程崩溃导致消息没发的窗口；先发 MQ、再提交 MySQL，又可能使消费者看见最终回滚的业务事实。

Outbox 的做法是：在同一个本地事务中写业务状态与“待发布事件”，提交后由 Relay 发布。数据库先保证“业务变化与发布意图一起保存”；MQ 暂时失败后还可以恢复发布。

当前 Relay 会认领事件，设置 30 秒处理租约，发布持久消息，等待最多 5 秒 Confirm，并检查不可路由返回；成功才标记 `PUBLISHED`。第五次发布失败标为 `PARKED`，等待处理原因后重放。数据库停车记录是恢复依据，停车队列发送失败也不能抹掉数据库记录。

| 概念／变量 | 含义 |
|---|---|
| `event_id` | 稳定事件身份，重投和人工重放仍用同一个 ID |
| Publisher Confirm | Broker 对发布的确认；不是消费者已完成业务的确认 |
| Consumer ACK | 消费端确认消息处理完成；业务事务失败时不能提前确认 |
| `consumer_name + event_id` | 每个逻辑消费者的去重标识，不同消费者可以各处理同一事件 |
| `attempt_count` | 尝试次数，用于有限重试 |
| `next_attempt_at` | 下一次允许重试的时间 |
| `locked_until` | 认领租约的截止时间，便于异常进程留下的任务被再次处理 |
| `PARKED` | 自动处理已经停止、保留错误摘要并等待修复的状态 |

最值得讲的故障窗口：Broker 已收到消息，但进程在标记 `PUBLISHED` 前退出，Relay 会重发；消费者已提交但 ACK 丢失，Broker 也可能重投。所以采用允许重投的投递方式，再用业务幂等保证效果只生效一次，不能宣称消息系统绝对 exactly-once。

Trade 消费支付成功事件时，消费去重记录、订单校验、状态迁移处于一个本地事务中；失败会连同去重记录一起回滚。Redis 结果投影不能加入同一个 MySQL 事务，当前秒杀结果处理先做可重复的 Redis 完成／条件补偿，再记录消费完成；失败重投依靠投影操作本身的幂等性恢复。

**6.2 秒杀的三层分别解决什么**

| 层 | 工作 | 不能单独保证的事情 |
|---|---|---|
| Redis Lua | 原子检查活动版本、时间、用户是否已参与、库存镜像；预扣并保存待处理请求 | 不代表最终订单已经创建，Redis 库存也不是最终事实 |
| RabbitMQ | 把已接纳请求异步交给建单消费者，分离入口接收与后续处理 | 队列本身不能防超卖；消费不足仍会积压 |
| MySQL | 条件扣最终库存、保存订单、预约唯一约束与结果事件 | 直接让所有流量争抢数据库仍可能有压力，故前置准入 |

实际代码比“Redis → MQ → MySQL”更具体：

```text
请求活动、用户身份与幂等键
  → Trade 检查活动、已有预约和 MQ 可用性
  → Redis Lua：扣镜像库存，记录用户资格、预约和稳定事件 ID
  → MySQL 本地事务：预约记录 + SeckillRequested Outbox
  → 返回 202，表示请求已接纳
  → Relay 将 Outbox 发布到 RabbitMQ
  → 消费者在 MySQL 事务中条件扣库存并创建订单，写结果事件
  → 结果消费更新 Redis 完成／补偿投影
  → 客户端查询预约获取异步建单结果
```

因此不能说入口完全不访问 MySQL；活动查询、已有预约检查以及预约持久化仍有数据库工作。MQ 探活也只反映当时状态，后续仍可能故障，可靠性最终依靠持久记录与重试。

**6.3 Lua 和数据库唯一约束如何配合**

Lua 把检查和修改放在同一个脚本中完成，避免两个请求都看到库存为 1 后各自扣减。当前脚本还保存 `user_id → reservation_no`，同一用户重复调用拿回原预约。

数据库用 `(campaign_id, user_id)`、预约号、事件号和订单关联等唯一约束，再次限制重复预约与重复建单。Redis 层用于准入；数据库约束用于最终正确性。

| 变量 | 中文含义 |
|---|---|
| `campaign_id` | 秒杀活动编号 |
| `campaign_version` | 活动配置版本，拒绝旧活动消息影响新配置 |
| `reservation_no` | 预约编号，202 返回后用于查询最终结果 |
| `stock` | Redis 中的库存镜像；区别于 MySQL 的 `available` |
| `pending` | 尚需处理／恢复的预约内容 |
| `pending-order` | 用于按时间扫描待处理预约的有序集合 |
| `KEYS` / `ARGV` | Lua 的 Redis 键列表／参数列表，不是数据库字段 |

Redis 键使用同一活动的 Hash Tag，例如 `{seckill:活动号}`，便于相关键在 Redis Cluster 同槽；当前本地环境并没有因此变成生产 Redis 集群。

**6.4 故障与补偿怎么回答**

- Redis 扣减后、MySQL 预约事务前退出：Redis 保存待处理请求和原事件 ID，恢复扫描可再次持久化；不能重新生成事件 ID 把同一意图变成新请求。
- 预约和 Outbox 已提交，MQ 故障：待发布事件保留，恢复后重试。
- MySQL 最终库存不足：建单事务回滚，再保存失败预约和拒绝结果；不能留下“有订单、没扣库存”的半成功结果。
- 收到失败结果：先核对数据库预约确实失败及活动版本，再用 Lua 条件补偿。当前补偿脚本删除待处理记录并只恢复一次库存，重复消息不应反复加库存。
- 稳定态发现 Redis 与 MySQL 不一致：没有未完成预约且活动版本相同才对齐库存，避免把进行中的预扣覆盖掉。
- Redis 或 MQ 不可用：关闭秒杀入口并返回受控错误，普通订单走自己的 MySQL 链路。

故障可恢复的前提是所需持久记录仍在。不能从上述测试推导出任意磁盘丢失、双端数据丢失或生产高可用能力已经得到验证。

**6.5 100 VU、吞吐、P95 和通过率的计算**

当前 k6 秒杀脚本是 `shared-iterations`：100 个 VU 共同完成 1000 次迭代；通过全局迭代编号取用户令牌，实现每个用户请求一次。VU 工作分配并不保证平均。[k6 shared-iterations 官方说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/shared-iterations/)

```text
吞吐速率 = 统计窗口内完成的操作数 / 对应统计时长
入口响应通过率 = 通过断言的次数 / 执行断言的次数
本次接纳占比 = 100 / 1000 = 10%
```

报告实际读取 `iterations.values.rate` 得到 1083.10；不是手工用测试开始与结束的任意两个时间戳重算。当前每次迭代只有一个入口请求，所以可以解释为该场景入口处理速率；其他一轮含多个 HTTP 请求的脚本，其迭代速率不能直接当作 RPS。

P95 可以理解为：把样本耗时从小到大排列，约 95% 样本不超过这个数，精确位置取决于统计工具的分位数算法。本项目报告读取 `http_req_duration` 的 `p(95)`。该 HTTP 指标包含发送、等待及接收时间，不含初始 DNS／连接建立时间；它也不包含返回 202 之后的异步排队和建单过程。[k6 指标官方说明](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)

脚本把 202、409 都定义为受控响应。因此 100 个接受、900 个 409 受控拒绝，可以同时得到 checks 100% 和 HTTP failure rate 0%。这里的状态码断言本身没有逐条验证拒绝原因；不能把所有场景中的 409 都解释为售罄。如需区分售罄、重复参与等原因，还应检查响应业务错误码。业务是否无超卖，还必须另查数据库的订单与库存，不能只看这两个百分比。

1000 个独立用户验证总体竞争；同一个用户并发 100 次验证重复资格；二者是不同测试。

性能数字来自 2026-08-25 的本地验收报告，硬件为 Ryzen 7 6800H、13.7GB 主机内存，Docker 分配约 6.6GB 内存。当前未找到报告引用的原始压测输出目录，因此学习时将它称为“历史报告结果”；正式演示前宜复跑当前版本并保存原始输出。这不是本次整理重新压出的结果。

可以用这段话应对秒杀追问：

> 我的重点是分层保证正确性。Redis Lua 做原子准入，预约与 Outbox 在 MySQL 中可恢复保存，MQ 异步驱动建单，最终库存仍用 MySQL 条件更新。测试是 100 VU 执行 1000 个独立用户请求，100 件库存最终有 100 单。1083 次每秒是包含售罄拒绝的入口处理速率，P95 约 259ms；它不代表成功建单吞吐或 1000 瞬时并发容量。

**七、推荐改造：从业务反馈到排序结果**

**7.1 为什么分召回、排序和重排**

用户打开页面时，系统需要从商品目录中找到可能有兴趣的书，再决定展示顺序，还要避免结果全是同一类目或同一卖家。

```text
已知的历史兴趣、当前场景与可用商品目录
  → 多路召回：热门、新品、内容、ItemCF、双塔向量
  → 候选融合、去重与补位
  → LambdaRank：结合用户与商品特征计算相对排序分数
  → MMR、类目和卖家配额、新品探索
  → Java 做最终业务过滤并关联推荐 delivery
  → 实际曝光、详情、加购、支付、退款反馈
  → Java 匿名快照 → 离线训练与评估 → 候选包验证与换版
```

| 方法 | 通俗解释 | 本项目中要讲清的边界 |
|---|---|---|
| 热门／新品 | 没有足够历史时也能提供结果 | 热门不能代替个性化效果证明 |
| TF-IDF 内容 | 用文字特征寻找相似内容 | 依赖目录内容质量，不等于理解所有语义 |
| ItemCF | 对被相似用户共同交互的商品建立关联 | 历史交互不足时效果有限 |
| 双塔向量 | 用户、商品分别编码为向量，用相似度召回 | 本轮精排实验冻结了已有双塔和召回包，没有重新训练双塔来取得本轮收益 |
| Faiss | 对向量执行高效检索 | 当前是 CPU `IndexFlatIP` 精确内积搜索；不能声称已验证百万级 ANN 集群 |
| LambdaRank | 学习同一候选组中哪些商品应排在前面 | 树模型输出是排序分数，不直接等于点击概率 |
| MMR | 在相关性与结果相似程度之间做取舍 | 还需结合业务配额；不能保证各指标同时提高 |

旧版三塔、DCN 属于与推荐负责人协作接入的历史经历。多任务 DCN 可以从“特征交叉、共享表示、多个任务头”理解；第三塔的实际输入和具体任务定义必须以第二版代码为准，不能凭名称猜测。当前主导成果的实现重点是双塔召回基础上的 LambdaRank、数据治理和可复现评估。

**7.2 双塔、LambdaRank、MMR 中的变量**

双塔可以写成下面的简化关系：

```text
u = 用户塔(用户输入)
v = 商品塔(商品输入)
相似度 s = u · v
```

`u`、`v` 是长度相同的向量；点积表示两者匹配程度。当前双塔编码做了归一化，因此内积对应余弦相似度。离线生成商品向量后，在线无需逐个执行商品塔。本项目双塔训练使用正对象和负对象的相似度 logits，配合交叉熵；`temperature` 控制 logits 的缩放，不能把它说成推荐成功率。

LambdaRank 按组训练：一个组对应一次用户候选比较，组内每个商品有特征 `x`、相关性标签 `y` 和预测分数 `s`。模型学习相对顺序，通常不把跨用户的任意两个分数拿来解释为统一概率。当前使用 LightGBM 的 `lambdarank` 目标，标签大小表示相关性等级；其标签增益与排序目标可配置。[LightGBM 4.6.0 参数说明](https://lightgbm.readthedocs.io/en/v4.6.0/Parameters.html#objective)

MMR 的核心可以简化为：

```text
选择得分(i) = λ × relevance(i) − (1 − λ) × max similarity(i, 已选对象)
```

- `i`：当前考虑的候选商品。
- `relevance(i)`：精排分数经过约定尺度处理后的相关性。
- `similarity`：候选与已选商品的相似度；相似惩罚有助于减少重复内容。
- `λ`：两种目标的权衡，当前默认是 0.8。它是算法参数，不是“准确率 80%”。
- 当前默认同类目最多 6 个、同卖家最多 3 个，同时尝试安排新品探索；候选不足时应如实返回短列表，不能靠重复商品填满。

**7.3 曝光、归因、标签分别是什么**

曝光是用户实际看到结果；推荐接口返回了某个商品，不能自动证明用户真的看到了它。当前服务端通过 delivery 关联推荐结果、用户、商品、位置、来源和模型版本，再接收合法的曝光／详情等反馈。完整页面是否正确上报，还需要实际前端联调验证。

| 字段 | 作用 |
|---|---|
| `request_id` | 标识一次推荐请求 |
| `recommendation_delivery_id` | 把后续行为关联到该次推荐中的具体商品记录 |
| `event_id` | 行为事件去重身份 |
| `user_key` | 使用外部秘密做 HMAC 后的稳定匿名用户标识；不是原始用户 ID，也不是随机每次变化 |
| `object_id` | 该推荐领域中的商品标识 |
| `event_time` | 行为发生时间 |
| `ingested_at` | 系统观察到／接收到该事件的时间 |
| `label_available_at` | 当时是否已经有足够信息形成训练标签的最早时间 |
| `model_version` | 哪个模型产生了这次推荐，用于比较、归因和回滚 |
| `data_source`／`traffic_origin` | 区分合成历史、脚本流量与自然业务来源；某个字段叫 REAL 不能单独证明存在自然用户流量 |

当前 Trade 原始事件样本转换使用的相关性标签为：曝光 0、详情 1、加购 3、下单 7、支付成功 15。下单可以作为较弱的正反馈，只有实际支付成功才代表购买完成。主动退货、质量问题等偏好负反馈可覆盖同归因链的正反馈；迟到支付等系统原因退款不直接当作用户不喜欢商品。

这与历史合成数据的标签分支不同：`_normalize_interactions` 遇到 `legacy_buy_signal` 时，按旧购买信号 7、加购 3、点击 1、其他 0 生成标签，并把购买信号标为 `LEGACY_BUY_SIGNAL`。旧数据中的购买字段不能冒充已核实的支付成功事实。阅读某轮指标时，要先确认使用的是哪一条数据转换路径。

没有观察到点击，也未必是负例：可能用户还没有看，或者支付事件还没到。当前真实曝光样本采用 30 分钟等待规则，并计算标签可用时间；这是本项目的工程设定，需要以后按业务延迟分布评审。历史合成实验中“未观察候选标零”的路径不能直接用于自然曝光数据。

**7.4 时间泄漏为什么会造成虚假提升**

假设要预测 2 月 1 日推荐什么，却使用了 2 月 10 日才发生的购买来计算用户偏好。模型在训练时已经看到未来答案，离线结果会虚高。

只把数据按日期切开仍不够。热门统计、用户兴趣、词表、召回索引和退款标签等也必须符合该请求时刻的信息可用性。例如行为 10:00 发生、10:10 才入库，在 10:05 的预测中不能使用它。

本轮明确训练截止、验证窗口和测试请求时刻，检查已使用标签的可用时间；按相同商品目录、公共历史过滤规则和请求时间评估模型。测试中 7581 个用户有目标记录，其中 7541 个存在符合公共目录及历史排除规则的正目标，进入主要质量指标分母。其余 40 人单独计数；有合法目标但没召回到的人仍保留，指标记为 0。

**7.5 训练组 5→500、特征 5→15 到底改了什么**

训练候选过少时，模型学习的是“少量简单选项谁更好”；服务却需要在大候选池里比较内容相近、兴趣接近的商品，训练任务和真实使用任务不一致。

本轮把训练候选组从最多 5 个对象改成实际 500 个对象，复用服务的候选生成、补位、历史过滤和特征提取入口。真实目标没有被召回时，不把正确答案偷偷塞进候选池。无正例的组不能为排序学习提供有效正负比较，但其召回失败仍计入完整评估。

这三个数字不要混淆：500 是本轮训练候选组大小；HTTP 实验中的 100／300 是请求候选参数档位；Recall@50 和 NDCG@20 的 50／20 是最终评估列表截断位置，都不是并发用户数。

| 特征组 | 数量 | 含义 |
|---|---:|---|
| 原有历史特征 | 5 | 历史热门比例、类目偏好、作者偏好、价格距离、新鲜度 |
| 新增召回信号 | 5 | 双塔相似度、是否已知用户、融合召回分数、分数是否缺失、热门倒数名次 |
| 新增来源标记 | 5 | TWO_TOWER、ITEM_CF、TFIDF、POPULARITY、NEW 是否命中，多个通道可同时为真 |

缺失标记很有用：补位商品没有融合分数，与一个确实算出 0 分的商品并不相同；仅用同一个 0 代替会丢失信息。旧精排分数也不能冒充新的召回相关性输入。

**7.6 为什么分数整体乘 0.25，也会改变结果**

如果只按分数大小排序，乘同一个正数不改变顺序。但 MMR 还减去相似度惩罚，相关性分数的尺度变化会改变这两项的相对大小。

例如两个候选相关性相近，一个与已选结果很相似。相关性分数范围过大时，相似度惩罚几乎不起作用；缩小相关性尺度后，多样性约束会更明显。

本轮最初扩展特征在验证集提高了 NDCG，却使覆盖率 52.60% 低于 54.31% 门槛，因此没有直接选用。之后在验证集比较 0.25／0.50／0.75 三档相关性尺度，选中 0.25：验证 NDCG 0.008190，覆盖率 54.93%。模型摘要冻结后才查看候选测试结果。

代码还支持同分百分位策略，但本轮最终选择是原始精排分数的 0.25 倍缩放，不能把“支持的策略”全部说成“最终采用的策略”。

**八、推荐指标：先会算，再解释提升**

**8.1 Recall@50 看的是有没有把相关商品找出来**

设用户 `u` 的合法相关目标集合为 `R_u`，推荐前 K 个商品集合为 `L_u(K)`：

```text
Recall@K(u) = |L_u(K) 与 R_u 的交集| / |R_u|
总体 Recall@K = 各个可评估用户 Recall@K 的算术平均
```

`|集合|` 表示集合元素数，`K` 是查看前多少个结果。例如某用户测试期有 4 个相关商品，前 50 个结果命中 1 个，该用户 Recall@50 就是 1/4=25%。分母是该用户的相关目标数，不是 50；命中数除以 50 是另一种指标 Precision@50。

项目是先算每个用户再平均，不是直接把所有用户命中数相加再除以所有目标数。两种平均方式对活跃用户赋予的权重不同。

这里统计的是完整推荐列表前 50 个的 Recall，不能简单称作 Faiss 单独召回率。即使召回模型冻结，精排或 MMR 把原本排在 50 名后的相关商品移进前 50，Recall@50 仍会提升。

**8.2 NDCG@20 看的是相关商品是否排在靠前的位置**

NDCG 是归一化折损累计增益。先给相关商品增益，再按展示位置折损，最后除以理想排序能取得的分数：

```text
DCG@K = Σ [ (2^rel_i − 1) / log2(i + 1) ]，i 从 1 到 K
IDCG@K = 将该用户所有合法相关目标按 rel 从高到低排列后的 DCG@K
NDCG@K = DCG@K / IDCG@K
```

| 符号 | 含义 |
|---|---|
| `i` | 展示名次，从 1 开始 |
| `rel_i` | 第 i 个商品的非负相关性标签；不相关商品为 0 |
| `2^rel_i − 1` | 标签对应的增益，高相关性获得更大权重 |
| `log2(i + 1)` | 位置折损，越靠后同样的相关性贡献越小 |
| `IDCG` | 理想排序的参照分数，不是模型实际分数 |
| `K=20` | 只累计前 20 个位置的分数 |

教学例子：某用户只有一本相关书，相关性设为 1。排第一时 NDCG=1；排第二时 NDCG=1/log2(3)≈0.6309；排在 20 名以后则 NDCG@20=0。这个例子只演示公式，不是项目测量值。

总体 NDCG 与 Recall 一样，先算每个用户，再对存在合法正目标的用户取算术平均。本轮主要指标分母为 7541 人；有合法目标但 Top20 完全没命中的用户计 0，没有合法正目标的 40 人记录为不适用并单列人数，不把他们混成“模型漏召回”。

当前 NDCG 代码对传入的 `gain` 标签再计算指数增益。历史标签 1、3、7 分别对应增益 1、7、127；原始事件路径中的标签 15 会对应 32767。它们是不同数据路径的规则，不能把原始事件的支付标签直接解释成本轮合成指标的权重。高等级标签权重很大，是需要继续评审的建模选择，不能简单说业务上“支付一定比详情重要 15 倍”。

精排训练／早停还使用同分期望 NDCG：若多个对象预测同分，不能因为原数据总把正例放在第一位，就把模型记成完美排序。完整服务列表评估和训练候选组评估是两个层次，不应把训练组较高分数当作全目录推荐效果。

**8.3 两个提升数字的实际计算**

比较对象是第三版上一轮正式反馈后模型与本轮候选模型，不是第二版旧 DCN 与第三版的直接对照。

| 指标 | 上一轮模型 | 本轮候选 | 绝对变化 | 相对变化 |
|---|---:|---:|---:|---:|
| Recall@50 | 0.0382707864（3.8271%） | 0.0496113311（4.9611%） | +0.0113405447，即 +1.1341 个百分点 | +29.6324%，简历写 +29.6% |
| NDCG@20 | 0.0032993462 | 0.0068533124 | +0.0035539661 | +107.7173%，简历写 +107.7% |
| 商品覆盖率@20 | 74.8802% | 70.7761% | −4.1041 个百分点 | −5.4809% |

```text
相对提升 = (优化后 − 优化前) / 优化前 × 100%
Recall 提升 ≈ (0.0496113311 − 0.0382707864) / 0.0382707864 × 100% = 29.6%
NDCG 提升 ≈ (0.0068533124 − 0.0032993462) / 0.0032993462 × 100% = 107.7%
```

为什么会超过 100%？这是相对原值的增长幅度，原值很小，翻倍就增长 100%。NDCG 本身仍是 0.006853 左右，远没有达到 1，更不能说准确率超过 100%。

商品覆盖率的分母是共同商品目录，分子是所有用户 Top20 中出现过的不同商品数。它衡量商品触达广度，不是用户覆盖率，也不等于冷启动效果。当前共同目录有 6262 件商品。

**8.4 为什么说结果有改进，但不能说已证明上线收益**

本轮实验使用固定合成历史数据和已查看过的历史测试窗口。合成数据能够帮助验证处理流程、比较算法行为；真实曝光偏差、用户意图与自然购买分布仍可能不同。因此报告将其限定为历史工程回归。

当前证据包括：固定用户与目录、统一请求时间、24 次参数试验、1987 条训练逐轮记录、三个固定随机种子。三个种子的历史 NDCG 分别约 0.006853／0.005750／0.006285，均值约 0.006296，说明结果有波动；简历的 107.7% 对应最终候选与上一轮模型，并非三种子平均提升。

本轮归档配对分析对同一批 7541 名用户计算 NDCG 差值，并做 2000 次用户重采样，95% 区间约为 [0.002119, 0.004963]。这说明该历史样本上的差异在此分析下较稳定，但不能消除合成数据、已经查看窗口和选择过程带来的局限。区间不等于“每个用户有 95% 概率变好”。

变化来自候选对齐、特征扩展与尺度校准的整体方案，没有证据把总提升精确拆成“某项贡献 70%，另一项贡献 30%”。

阅读训练日志时，还要认识下面这些变量：

| 名称 | 含义 | 本轮如何理解 |
|---|---|---|
| `trial` | 一套超参数配置的一次试验 | 五项和十五项特征各 12 次搜索，总计 24 次；不是 24 名用户 |
| `seed` | 随机种子，控制抽样等随机过程 | 用多个固定种子观察波动；同种子复现也需要相同数据、代码和环境 |
| `epoch`／`round` | 神经网络常用 epoch 表示遍历训练集一次；提升树常用 round 表示一轮提升 | 1987 是本轮汇总的逐轮日志数，不能说成单个双塔训练了 1987 个 epoch |
| `learning_rate` | 每轮模型更新的步长系数 | 是训练参数，不是模型质量提升率 |
| `num_leaves` | 一棵树允许的叶子数量上限 | 控制模型复杂度，需要验证是否过拟合，不是越大越好 |
| `early_stopping` | 验证指标持续未改善时停止训练的规则 | 当前精排训练使用修正同分偏差后的验证指标；不能看测试集决定何时停止 |
| `feature_schema` | 特征名称、顺序与维度的约定 | 训练第 6 列和服务第 6 列必须同义，仅仅列数一致还不够 |

训练工作的顺序可以记为：

1. 冻结数据、来源、时间窗口、代码及基线模型。
2. 检查标签成熟时间、归因、候选组和特征口径。
3. 用训练集拟合，在验证集搜索参数及校准分数。
4. 选定候选并冻结摘要，再做固定历史窗口评估，记录多个种子的波动。
5. 在隔离容器核验兼容性、真实 HTTP 请求、资源占用和换版回滚。
6. 综合质量、覆盖率和性能决定是否晋级；失败保留记录，不修改门槛来制造通过。

已知的代价和限制要能回答：

- 覆盖率下降约 4.10 个百分点，不能只报 NDCG 上升。
- 固定冷启动组只有 10 人，不足以声称冷启动覆盖率稳定提升 30%。
- Python 最终 47 项测试通过；Linux／Windows 代表性响应 180/180 一致，旧包兼容对比 135/135，但这不是对所有输入的完整证明。
- 正常 HTTP 采样共 27761 次，包含优化前和优化后场景，不能全部写成本轮候选独有请求数。
- 候选在 300 候选、20 VU 条件下 HTTP P95 为 307.6ms，高于本轮 300ms HTTP 门槛；进程内推断 P95 约 166～176ms，两种口径不能混用。
- HTTP 采样每档为 60 秒；额外持续负载为 120 秒且带思考时间，不能称为已完成 30 分钟长稳。
- 最终决策为 `NOT_PROMOTED`／`ENGINEERING`：候选完成实验但未替换当前业务工程模型，更没有自然流量 A/B 收益。

**8.5 模型包、换版与回滚是什么**

模型包不只是一个权重文件，还应包含词表、特征顺序、预处理约定、索引、数据摘要和模型版本。训练时 ID=5 与服务时 ID=5 若对应不同商品，即使网络正常也会推荐错对象。

当前加载会校验模型包与映射一致性，坏包或越界指针不能替换已加载的可用模型；活动指针用于原子切换，回滚恢复原指针。原子指针更新不意味着全量包瞬时加载：本轮 6GiB／4 CPU 隔离容器的三次激活／回滚约为 20～22 秒，测量包含调用方校验与服务端加载。

2GiB 容器最初加载失败与热切换容量不足是已记录失败；不能跳过资源条件，只背后来的成功结果。新旧包并存时的内存峰值也是上线评审需要考虑的成本。

推荐升级可以这样口述：

> 我主要修正了训练与实际推荐任务不一致的问题，包括时间信息可用性、反馈归因和候选特征口径。最近一轮冻结已有召回，把精排训练组从最多 5 个对象扩成 500 个，特征从 5 项增加到 15 项，再校准精排分数与 MMR 的尺度。在相同合成历史集和用户分母上，Recall@50 从 3.83% 到 4.96%，相对增长 29.6%；NDCG@20 从 0.003299 到 0.006853，相对增长 107.7%。这是第三版内部的离线改进，覆盖率有下降，HTTP 最重档还有延迟问题，因此候选没有直接晋级。

**九、常见追问与回答要点**

| 面试追问 | 先回答什么，再补什么 |
|---|---|
| 你个人负责哪些？ | 第一版前端独立完成、微服务改造主导、当前支付秒杀与推荐升级主导；旧推荐接入是协作成果，再具体说明你修改的模块 |
| 为什么不用一个 Redis 分布式锁解决全部并发？ | 单个锁不能替代数据库事务和唯一约束，也不能覆盖消息重投与资金状态；分别讲准入、事实与幂等 |
| Outbox 会不会重复发？ | 会。举 Confirm 已成功但数据库未标记的窗口，再讲稳定 event_id 和消费幂等 |
| 100% 检查通过是不是人人抢到？ | 不是；100 接受、900 受控拒绝都符合预期，实际接纳占比为 10% |
| 为什么有 Redis 还要扣 MySQL 库存？ | Redis 是库存镜像与准入，MySQL 才是最终事实；补偿和重建也以事实为准 |
| 1000 用户是不是 1000 并发？ | 不是。100 VU 完成 1000 用户各一次请求；另一次 1000 VU 预检有连接失败，不能用正式结果宣称千级瞬时并发 |
| P95 好看是否意味着系统稳定？ | 还要看 P99、失败率、队列积压、资源和持续时长；入口 P95 不能覆盖异步落库耗时 |
| 是否接过真实支付？ | 当前证据为 Mock 渠道和真实 MySQL 集成测试；可以讲协议与一致性设计，不冒充真实渠道生产验证 |
| 为什么 NDCG 提升 107.7%，看起来却只有 0.0068？ | 前者是低基线上的相对增长，后者是指标绝对值。说明数据规模、稀疏目标和评估口径，再说明自然数据验证尚缺 |
| 召回冻结了为什么 Recall 还能提高？ | 这里是最终 Top50 Recall；精排和重排可以把候选池中已有的相关对象移入前 50 |
| 为什么增加特征未立即选用？ | 第一次验证虽然 NDCG 上升但覆盖率低于门槛，随后仅在验证集校准尺度后才冻结候选 |
| 没曝光的商品能当负例吗？ | 不能一概而论。用户可能未看到，项目合成实验的未观察零标签路径不能直接套到自然数据 |
| 新模型上线了吗？ | 候选完成离线和隔离服务测试，但最重 HTTP 档未达门槛，仍未晋级 |
| 下一步你会做什么？ | 独立未来窗口和自然曝光数据、扩大冷启动样本、剖析 HTTP 与加载成本，按固定条件复测；不用测试集反复调参 |
