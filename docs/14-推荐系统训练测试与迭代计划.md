# 推荐系统训练、测试与迭代计划

- 制定日期：2026-09-06。
- 适用范围：新工程 Trade 推荐、Python 训练与推断，以及 Gateway → Trade → Recommendation → Mock Payment 的本地验证链路。
- 当前状态：已检查本机资源并形成计划；下表 R1～R7 尚未执行。环境检查与历史结果不代表新一轮训练已经通过。
- 决策依据：[ADR-0003](adr/0003-推荐服务与双域数据闭环.md)、[现有实验协议](../linkverse-platform/recommendation-experiments/protocol.md)、[本次环境记录](../linkverse-platform/recommendation-experiments/iterations/20260906-准备记录.md)。

## 1. 目标与完成条件

本轮先修复会影响结论的实现，再训练、比较和验证候选模型。每次迭代必须能回答：改了什么、为什么改、在哪份数据上验证、指标如何变化、付出了多少资源、是否保留，以及失败时如何回退。

完成交付需要同时具备：

1. 可信评估器、固定数据切分和可重复的旧模型校正基线。
2. 曝光、详情、加购、支付和退款能正确归因，训练特征与负反馈均满足时点约束。
3. 候选补位后的最终列表遵守业务过滤、去重与重排规则，模型加载失败仍能继续服务旧版本。
4. 至少一次完整的受控调参、三种子重训和逐组件对照实验。
5. 本地 HTTP 反馈、快照、重训、再推荐，以及性能、故障和回滚的实测证据。
6. 持续保存原始观测和中文迭代记录，最终自动汇总升级步骤。

线上业务收益需要另有真实自然用户数据及前瞻实验。脚本驱动的 HTTP 操作即使经过真实服务和 Mock 支付，也只能证明工程行为和模拟条件下的效果。

## 3. 迭代顺序与阶段门槛

| 轮次 | 单轮目标与主要工作 | 本轮必须留下的证据 | 进入下一轮的条件 |
|---|---|---|---|
| R0 | 环境检查、冻结旧模型/数据/代码、建立指标目录和采集器 | 环境快照、文件哈希、命令与退出码、旧报告引用 | 采集器冒烟通过，运行编号唯一，旧产物不可覆盖 |
| R1 | 修正评估模式、统一用户与候选口径、修复空标签和假会话统计 | 评估回归测试、旧模型重复复评、校正后的全量基线 | 同一冻结模型与数据重复结果一致；未执行与无标签不再记成 0 |
| R2 | 修复 delivery 导出、时间可见性、标签成熟、数据来源隔离 | Java → JSONL → Parquet → 标签的贯穿测试与数据审计 | 同链合并、退款分类、未来信息隔离和快照一致性全部通过 |
| R3 | 修复最终重排、训练/推断特征一致性、坏包保活及上下文使用 | 列表约束测试、特征对照、并发换版与坏包测试 | 最终返回列表满足约束；坏包不影响旧模型正常请求 |
| R4 | 小规模试训、受控调参、三种子重训与逐组件对照 | epoch 曲线、trial 表、种子结果、资源曲线、模型卡 | 开发集 NDCG 高于热门与当前有效模型，覆盖率至少为当前模型 90%；冻结候选后才能运行确认性评估 |
| R5 | 本地 HTTP 反馈闭环、导出、反馈后重训与再推荐 | 逐链路断言、事件漏斗、归因审计、前后模型同口径比较 | 支付/两类退款/曝光成熟均有成功证据；并非全量降级补位 |
| R6 | 推荐专用压力、故障、长稳与回滚测试 | 各层延迟、吞吐、降级比例、资源、恢复时间、回滚记录 | 20 并发门槛和正确性通过；瓶颈及未通过项有明确结论 |
| R7 | 汇总迭代步骤、检查发布门禁并形成候选结论 | 迭代总表、趋势图、最终模型卡、复现命令、回滚步骤 | 每项结论有原始证据；区分本地候选与真实业务收益 |

R0 的环境检查已开展，其余工作仍按顺序实施。正确性修复即使暂时降低 NDCG，也必须保留；以修复后的系统重新建立可优化基线，不以恢复错误实现换取更高分数。

R4 没有产生更好的算法候选时，保留修复后的有效对照，记录本轮不晋级；R5/R6 仍可用该对照或隔离工程夹具完成链路测试。确认性数据不足也不阻止这些工程工作，但不能关闭对应的质量证据待办。

### 3.1 R1：评估正确性

- 评估时显式切换 `model.eval()`，关闭梯度，结束后恢复调用方所需模式；覆盖 Dropout 的重复性测试。[PyTorch 2.9 文档](https://docs.pytorch.org/docs/2.9/generated/torch.nn.Module.html#torch.nn.Module.eval)说明了评估模式与关闭梯度的区别。
- 全量评估为主，五类画像只作解释性案例。记录所有测试用户、共同已知用户、冷启动用户的分母，不静默丢掉 OOV。
- 无正标签会话的 NDCG/Recall 记为不适用，单列数量；覆盖率、合法性和延迟仍可测。整体报告同时给出可评估比例，避免通过排除难例抬高指标。
- 使用真实会话/请求边界；合成数据没有会话时，明确采用预先定义的时间窗，禁止把相同调用重复三次称为三次动态反馈会话。
- 热门基线、旧模型、新模型使用相同用户集合、查询时点、候选可见集、历史过滤和标签规则。
- 同时评估召回池、精排、重排、Trade 最终输出；分别报告候选遗漏和后续排序损失。
- 原排序模型的“1 个正样本加最多 4 个负样本”验证分只作训练诊断。对外报告的 NDCG 必须在真实召回候选或完整可见目录上计算。

### 3.2 R2：数据与反馈正确性

- 导出并校验 `recommendation_delivery_id`，确保推荐展示、详情、加购、订单、支付及退款属于同一归因链。缺失关键关联时拒绝进入归因质量评估，并报告原因。
- 负样本除了商品已发布，还必须满足负反馈在样本时刻已经可知。覆盖“未来退款不能影响过去训练样本”和“未来支付不能回填历史特征”的反例。
- 依照现有规则区分用户主动/质量退款与运营补偿退款；同链多行为按冻结的标签规范聚合，保存标签版本和产生依据。
- 保留 30 分钟曝光成熟规则；新增曝光不能立即当负例。组件测试使用受控时钟；HTTP 验证使用预先建立的到期曝光或实际等待，不篡改业务时间冒充等待完成。
- 事件时间、采集时间、标签可用时间和快照截止时间分别保存；迟到事件、跨窗口归因链要有统一归属与排除规则。
- 商品历史价格、状态和发布时间需满足时点可见性。只有当前商品快照时明确其限制，不将“已删除聚合字段”等同于已消除所有泄漏。
- 记录导出水位和一致性边界；商品与事件读取需要同一可解释快照，JSONL 转换前校验原文件哈希和对象参照完整性。
- 旧 CSV 合成数据、本地脚本流量、真实自然用户流量分开存储、训练和评估。本地接口当前写入 `REAL` 不足以证明自然流量；补充 `traffic_origin=SCRIPTED`、`environment=LOCAL_TEST` 等来源元数据并强制检查，禁止与自然流量混合。

### 3.3 R3：训练与推断一致性

- 统一热门权重、时间衰减、价格归一化和用户偏好的实现；统计量只由允许的拟合窗口生成，并随模型包保存具体数值。
- 将候选补位纳入最终重排。验收对象是用户实际收到的 TopK，覆盖 Python 补位和 Trade 可售过滤后的再次补位。
- 分类/卖家配额、去重、已购/购物车/不可售过滤、新品探索比例分别断言。可用目录不足时返回明确短列表或按显式策略放宽软约束，并记录放宽原因；库存、权限等硬约束不可放宽。
- 新模型在请求关键路径之外加载和校验；失败继续使用旧模型，失败版本有退避和去重，避免所有请求重复加载坏包。验证并发换版时版本与候选不混杂。
- 原子激活前检查工程证据和模型用途；不能仅因文件哈希正确就作为合格候选。实验性激活只能使用隔离测试模型根目录，并写明用途。
- 激活清单包括包完整性、特征/标签/接口兼容、完整加载、预热和样例推断，预先保存旧活动指针及模型版本；发布后同时核验指针、内存加载版本和实际请求版本。
- 为 HOME/DETAIL/CART 定义各自需要的上下文；上下文来源与读取权限先明确，再接入推断。近期兴趣可从 Java 提供的只读上下文或版本化快照取得，Python 不直接写业务库、Redis 或 ES。
- 保存并测量热门/新品冷启动路径和 OOV；不能用已知用户的平均提升掩盖冷启动退化。

## 4. 数据切分与实验设计

### 4.1 三条独立证据线

| 数据线 | 用途 | 允许的结论 |
|---|---|---|
| 现有 94,934 条合成交互 | 修复回归、算法开发、训练吞吐与可重复性 | 合成条件下的相对效果及工程正确性 |
| 本地受控 HTTP 流量 | 事件归因、训练闭环、故障与性能 | 本地链路通过与模拟反馈响应 |
| 后续自然用户数据 | 前瞻留出评估、影子与线上实验 | 满足实验设计后的真实业务收益 |

当前最终 15% 窗口已经被多次查看，应视为历史回归集。不能继续在该窗口选择配置后再声称盲测。开发阶段使用较早时间段内的固定滚动验证折；确认性评估使用提前冻结、尚未查看的新留出数据。若新数据尚未积累，只出回归和工程结论，不把自然流量缺失当作无法继续本地工作的理由。

把 `split-manifest.json` 作为待实现的切分真值，记录绝对时间边界、事件/查询集合摘要、归因窗口、剔除原因和数据来源。初始/反馈模型必须引用同一份切分定义；不能对 before/after 两份增长中的数据分别按百分比重切，再直接比较。

F0/F1 的共同评估查询必须发生在 F1 允许的拟合截止时间之后。F0 只读取基础拟合窗，F1 只额外读取独立反馈窗；共同评估的目标事件、delivery、订单及归因链不得进入任一模型拟合数据。自动校验事件与归因链集合的交集，不能只比较切分文件名是否一致。训练时延造成的模型可用时间差另行记录，不用回填数据伪装当时已有新模型。

每个查询记录预测时点与当时可见特征；未来标签仅供评估。跨边界的同会话、同订单或同 delivery 不拆成训练与测试的互相泄漏样本；必要时设置隔离间隔并报告损失样本数。

### 4.2 对照矩阵

先固定数据和评估器，再改变组件，最后改变反馈数据量。所有对照使用一致的调参预算和时间窗口。

| 编号 | 对照内容 | 目的 |
|---|---|---|
| B0 | 冻结旧模型，在修正后的评估器上复评 | 区分“计算口径修复”与“模型提升” |
| B1 | 时间衰减热门＋新品 | 提供简单、可运行的基线 |
| B2 | TF-IDF、ItemCF、双塔分别评估 | 确认各通道的命中、覆盖与代价 |
| B3 | 多路融合，逐个移除通道 | 测量通道独立贡献和重复候选比例 |
| B4 | B3 加统一特征的 LambdaRank | 确认精排是否改善真实候选排序 |
| B5 | B4 加最终 MMR/配额/探索 | 测量相关性、多样性、覆盖和业务约束的取舍 |
| F0/F1 | 相同冻结配置，分别使用反馈前后拟合窗口 | 单独测量新增反馈的作用 |
| C0/C1 | 同一模型快照，分别关闭/开启近期上下文 | 测量上下文贡献，避免混同重训收益 |

### 4.3 训练预算与复现

1. 冒烟：双塔 5 次、LambdaRank 5 次，检查日志、显存、时点和模型包；冒烟结果不用于晋级。
2. 首轮正式搜索：沿用双塔 30 次、LambdaRank 50 次；双塔最多 40 epoch、patience 5，AMP 保持现有策略。正式搜索参数和预算在运行前固化。
3. 最优配置使用 `20260903`、`20260917`、`20261001` 三个固定种子重训；记录每种子分数、均值和标准差。双塔和排序器都显式记录种子与随机参数。
4. 选取实际部署模型只依据开发验证集；不得查看确认性测试后再挑最优种子。保存所选种子及选择理由。
5. 反馈后对照复用所选超参数与训练轮数策略。需要重新调参时另开实验编号，避免把“增加数据”和“增加搜索预算”混为一项收益。
6. 同一种子重复完整训练一次，比较评估指标、向量及预测；硬件差异和非确定性容差事先写入配置，文件中的时间戳差异不作为算法不可复现。
7. 仅在开发验证集仍有收益且资源允许时增加搜索预算；失败 trial、OOM 和中止都保留。达到预算且无改善时转向误差分析，不无限堆 trial。

验证集用于日常曲线与选择；未打开的确认性测试集在候选冻结后评一次。如果根据该结果再次改模型，该集合从此转为开发/回归用途。

## 5. 必须持续收集的指标

| 层次 | 指标 | 频率与切分 |
|---|---|---|
| 数据 | 用户/商品/事件/有效标签数、重复率、OOV、缺失归因率、成熟曝光数、负样本来源、跨窗排除数、迟到事件比例 | 每个快照、每次切分；按来源和时间窗分组 |
| 双塔训练 | train loss、验证 NDCG@20/Recall@50、学习率、epoch 时间、样本/秒、梯度异常、AMP 跳步、显存峰值、最佳 epoch | 每 epoch；按 run/trial/seed 关联 |
| 排序训练 | 训练与验证损失/排序指标、最佳树轮数、候选组大小、硬负样本占比、特征统计差异 | 每个评估轮次及 trial 结束 |
| 全链离线 | NDCG@20、Recall@20/@50、HitRate@20、覆盖率、列表多样性、新颖度、类目/卖家分布、退款相关误推 | 每个模型和每个管线阶段 |
| 分群 | 冷启动、历史稀疏、活跃、单兴趣、多兴趣、价格敏感、新品；每组样本数与不适用比例 | 每次正式评估 |
| 在线质量与正确性 | 去重/过滤/配额通过率、短列表率、候选填满率、模型版本分布、全量/部分降级率、重复请求列表变化 | 每个请求的脱敏记录与汇总 |
| HTTP 性能 | 成功率、有效模型响应率、p50/p95/p99/max、RPS、超时/拒绝率、各阶段耗时、在途并发 | 逐请求原始测量；每 10 秒形成时间序列 |
| 业务反馈 | 曝光→详情→加购→支付漏斗、主动/运营退款、归因覆盖、反馈到模型可见延迟 | 每条验证链及窗口；脚本流量不称线上 CTR/CVR |
| 资源与恢复 | GPU 使用/显存/温度，进程 CPU/RSS，容器 CPU/内存，磁盘增长，队列积压，模型加载/故障恢复/回滚时间 | 每 5 秒及故障前后 |

所有数据点至少带 `run_id`、`iteration_id`、UTC 时间和单位。配置元数据另外记录 Git 提交、工作区源代码摘要、数据哈希、切分哈希、模型版本、特征/标签/评估器版本、种子、依赖、并发数与 candidate_count。

摘要用于确认身份，不能恢复代码。每轮另存经过敏感信息检查的源码快照，或保存可访问的 Git 提交、完整变更补丁及运行所需的未跟踪源码；依赖锁文件与脱敏配置一并留档。凭据从现有受保护配置重新注入，不进入快照。

用户标识只用匿名 key，原始请求体、访问令牌、密码与支付敏感内容不进入结果文件。Prometheus 标签维持低基数；run/trial/user 等高基数关联放到本地结果记录，不直接作为在线指标标签。

缺测使用 `null` 并记录 `NOT_RUN`、`NOT_APPLICABLE` 或失败原因。零仅表示真实测得的零。每个率指标同时保存分子、分母；百分位从逐请求观测或可合并直方图计算，不平均各批次的 p95。

新旧模型按同一用户/会话配对比较，报告绝对差和相对差；旧值为 0 时不计算相对提升。以用户为重采样单位计算 95% 配对 bootstrap 区间，避免把同一用户的多次会话当作独立用户。三种子波动与用户采样区间分别报告。

## 6. HTTP、性能与故障测试

### 6.1 本地链路准备

1. 验证四个 Java 服务健康、推荐 readiness、服务 JWT 和 HMAC 配置；配置值只检查存在性和正确性，不输出密钥。
2. 为本轮创建可追踪的本地测试账号、商品、库存与行为集合。关联 `run_id`，使用可恢复的隔离数据；Python 只通过 API 驱动业务，快照导出保持只读。
3. 确认训练商品 ID 与本地 Trade 商品目录一致，匿名用户 key 使用相同版本的 HMAC 规则。旧合成模型的商品编号不能默认当作当前 Trade 的商品编号。
4. 为 HTTP 验证训练独立的本地脚本数据模型包；与旧 CSV 实验产物和自然用户模型分开。小数据量不足以训练时，可使用明确标记的工程夹具模型验证协议，再积累数据完成训练闭环。
5. 推荐专用测试必须断言 `model_version`、候选命中及 `fallback` 分布，防止“全由数据库降级返回 200”被记为模型链路成功。

### 6.2 功能与事件闭环

最低保留 5 类画像，每类至少 3 个不同的请求上下文，并覆盖以下确定性分支：

- 曝光未转化且已成熟；曝光后详情与加购；下单支付成功。
- 用户主动/质量退款；运营补偿退款；重复、迟到及乱序支付/退款事件。
- 无历史用户、新用户产生第一条反馈、新上架商品、缺货/下架、已购和购物车过滤。
- 推荐接口失败后的数据库降级，以及推荐恢复后的模型响应。
- 导出前后事件数与水位对应；同链标签、数据来源、负样本时间约束正确。
- 反馈后完整重训，在同一冻结比较集上评估，并通过 API 再次读取新模型版本。

支付与退款测试要有确定命中的用例，不依赖“恰好推荐到目标商品”。自然推荐是否命中另作质量指标。回放脚本需强制检查转化、两类退款和最终业务状态；仅记录 `refund_executed=false` 不能算闭环通过。脚本模拟展示只证明曝光协议，真实前端的可见性埋点另行验收。

### 6.3 分层性能测试

| 测试层 | 方案 | 输出 |
|---|---|---|
| Python 进程内 | 先复用现有 20 并发/400 次/candidate_count=300 基准；正式稳定性至少 3 次，每次至少 2,000 次调用 | 推断分位、吞吐、资源与候选数 |
| Python HTTP | 带服务 JWT，包含序列化和模型注册表；冷加载与热运行分开 | JWT/模型加载/推断耗时与响应正确性 |
| Gateway → Trade → Python | 1、5、10、20 并发逐级测试；每档预热 30 秒、采样至少 2 分钟，并记录实际完成请求数 | 用户可见延迟、有效模型率、降级、落库与数据库耗时 |
| 容量探索 | 20 并发达标后再尝试 30、50；达到瓶颈即停止增加 | 限流、信号量拒绝、连接池与数据库瓶颈 |
| 长稳 | 标准 20 并发下持续 30 分钟；至少一次独立低噪声复跑 | 内存增长、连接泄漏、令牌更新、队列和错误趋势 |

压测候选数同时覆盖日常 Top20 对应请求规模及 300 候选压力规模，不混为同一性能结论。性能阶段停止 GPU 训练和 Java 构建；记录其他项目负载，不主动终止它们。

ADR 的基本门槛：20 并发成功率 ≥99%，Python 内部推断 p95 ≤300ms，Trade 推荐 p95 ≤800ms。Gateway 总延迟单列。非故障阶段同时检查模型实际被调用和结果有效性；故障阶段的降级成功另算。

新增本地验收门槛：正常已知用户和冷启动两组分别要求有效模型响应率 ≥99%、非预期降级率 ≤1%。有效模型响应指 HTTP 成功、版本为预期活动版本、结果字段/业务过滤正确，且未用数据库降级冒充模型结果；分母为该组所有预期使用模型的请求。冷启动经模型包的热门/新品通道返回属于有效模型响应。特意构造的目录不足、故障和拒绝请求单列，不混入正常组；普通组需要充足可售夹具商品。模型响应与数据库降级响应的延迟分开统计。

每次 HTTP 对照冻结工作负载：测试用户/商品夹具版本、请求序列或生成种子、场景比例、思考时间、候选数、账号令牌生命周期、缓存初始状态和预热方式。敏感令牌不留档；保存获取方式及有效期策略。改变负载或服务配额必须另开对照，不能归因于模型升级。

800ms 的远程超时等于 Trade 总 p95 预算，留给 JWT、数据库、补位和落库的余量不足。先分解耗时，再单独调整内部超时与资源限制；不能把总预算直接复制到每个内部步骤。

### 6.4 故障与回滚

按轮次对 Recommendation 专用进程/容器注入超时、连接失败、坏模型包、无活动模型、并发换版、错误服务令牌和容量拒绝。断言：

- 无权限请求被拒绝；推荐异常不会绕过 Trade 权威过滤。
- 有旧模型时坏包不造成持续失败；无旧模型时 readiness 清晰失败，Trade 可控降级。
- 熔断按既定窗口打开、半开并恢复，重复失败不会无限重试。
- 活动版本回退后真实请求返回旧版本；记录切换期间成功率、混版和恢复时间。
- 健康测试数据中的曝光/支付/退款不因重复事件增计；消息收敛后做只读核对。

故障范围以本轮资源清单为准。清理仅覆盖本轮创建且已核对归属的临时资源；保留已有容器、卷、模型包和用户工作区修改。不得执行全局 Docker prune 或删除整个业务卷。

本地候选激活后的回滚触发值在运行前冻结：非故障观测中，连续 3 个 30 秒窗口出现错误率 >1%、非预期降级率 >1% 或 Trade p95 >800ms，则回到预先保存的旧指针；每窗至少 100 个有效观测，不足时延长采样，不能算通过。候选无法加载/预热或版本错配则立即拒绝激活，不等待统计窗口。回滚执行后，目标是在 30 秒内由 readiness 与连续实际请求确认旧版本恢复；该时限为本计划新增的本地验收目标，未测不能标为通过。预期故障注入按用例执行和恢复，不把故障期纳入普通发布观测。

回滚复用现有 `serving.activate` 对旧包原子切换，并以旧包的已保存路径和版本为参数；额外验证当前进程真正加载了旧包，不能仅检查磁盘指针。数据修复使用向前兼容方式，回退模型不回滚支付事实或删除反馈。

## 8. 指标存档与升级步骤总结

复用 `recommendation-experiments/runs/<run_id>/`。新轮次采用独立目录，禁止覆盖历史运行；计划中的新增文件由统一实验入口生成。

| 文件/目录 | 内容 | 保存规则 |
|---|---|---|
| `manifest.yaml`、`config.json`、`split-manifest.json` | 实际代码、数据、配置、切分和依赖身份 | 脱敏后保留，生成即冻结 |
| `raw/source/`、`workload-manifest.json` | 可重建的非敏感源码版本与 HTTP 夹具/负载身份 | 源码快照本地保留；公开摘要不含凭据 |
| `raw/epoch-metrics.jsonl`、`raw/resources.jsonl`、`raw/stages.jsonl` | 训练曲线、资源与阶段事件 | 原始观测，Git 忽略 |
| `trials/` | 每次 trial 参数、完成/失败/剪枝、指标和耗时 | 完整保存于本地，Git 忽略 |
| `raw/http/`、`raw/tests/` | 脱敏请求测量、测试结果、故障时间线 | 不含令牌与原始个人信息，Git 忽略 |
| `offline-metrics.csv`、`cohort-metrics.csv`、`ablation.csv` | 全量、分群、对照与分母 | 从原始结果生成；注明评估器版本 |
| `comparison.md`、`model-card.md`、`iteration.md` | 中文结论、限制、保留/回退决策 | 可审查的 Markdown |
| `plots/` | loss/验证指标、trial 最优值、资源、漏斗、离线指标、延迟和故障趋势图 | 标明数据源、单位和误差范围 |

每次迭代结束立即填写[迭代记录模板](../linkverse-platform/recommendation-experiments/iteration-template.md)，不等所有试验结束后凭记忆补写。失败迭代也占一个记录，注明后继轮次及修复原因。

最终升级说明按“原始问题 → 校正基线 → 数据修复 → 训练调整 → 推断修复 → HTTP 验证 → 门禁与回滚”组织，并提供逐轮表：

| 轮次 | 变更/假设 | 数据与评估器版本 | 前值→后值 | 资源/耗时变化 | 结论 | 证据与下一步 |
|---|---|---|---|---|---|---|
| 待实际执行后生成 | 不预填效果 | 不同口径单列 | 未执行使用不适用 | 不预填耗时 | 保留/回退/待补证据 | 精确到运行文件 |

不把评估修复带来的数值变化记为算法收益；不把全量数据结果与五画像结果连成同一趋势；不把训练时间复制成双塔和排序各自耗时后相加。新增指标采集必须分组件计时。

原始证据在最终总结完成前完整保留。之后的归档与删除按实际磁盘需求单独处理，不在训练结束时自动清除失败试验。

## 9. 候选验收与后续阶段

| 维度 | 门槛 | 性质 |
|---|---|---|
| 评估与数据正确性 | 重复评估一致；归因、未来信息隔离、数据来源检查通过 | 必须通过 |
| 推荐效果 | 同一口径下 NDCG@20 高于热门基线与当前有效模型，覆盖率不低于后者 90% | 现有 ADR 门槛 |
| 统计证据 | 同用户配对提升的 95% 区间下界大于 0，且三种子稳定性和分群退化可解释 | 本计划新增的确认性证据要求 |
| 最终列表 | 硬过滤、去重正确；配额/探索满足规则或有明确短列表/软约束原因 | 必须通过 |
| 性能 | 20 并发成功率 ≥99%；Python 内部 p95 ≤300ms；Trade p95 ≤800ms | 现有 ADR 门槛 |
| 正常模型可用性 | 已知用户/冷启动分别有效模型率 ≥99%、非预期降级率 ≤1%；按冻结负载评估 | 本计划新增门槛 |
| 故障与回滚 | 坏包保活、并发换版、熔断恢复及回退后实际请求成功 | 必须实测 |
| 证据完整性 | 原始指标、配置、种子、测试命令与退出码齐全，缺测明确 | 必须通过 |

门禁按候选用途应用，不能把未执行的确认性评估当作通过：

| 候选用途 | 必须满足的证据 | 允许保留的缺口 |
|---|---|---|
| 工程夹具 | 包/契约/安全正确，用途与数据来源明确，只在隔离环境验证指定功能 | 训练效果、性能和统计门槛可为 NOT_RUN；不能晋级质量候选 |
| 本地回归候选 | 数据/评估正确性、同口径回归质量、最终列表、正常可用性、性能、故障与记录通过 | 新留出集与确认性统计可以 NOT_RUN；R7 仅完成工程总结 |
| 本地确认性候选 | 本地回归候选的全部证据，加未查看的新合成/脚本留出集与确认性统计通过 | 自然用户收益仍为 NOT_RUN；不得宣称真实转化提升 |
| 自然流量候选 | 对独立自然流量满足相应离线与工程门禁，完成规定的影子验证 | 上线因果收益仍要由前瞻线上实验确认 |

因此，没有新留出数据时可以完成本地回归候选及其升级步骤总结，但确认性质量门禁保持待补证据。仅有合成或脚本数据时，不得把自然用户收益状态改成已完成。

这一轮完成后，再按误差分析选择下一项改进：内容特征进入双塔、近期兴趣、冷启动、新品覆盖或曝光偏差处理。每次只改变一个主要假设，继续沿用同一记录与回滚方式。Forum 与新的复杂模型不在本计划的首轮实施范围。
