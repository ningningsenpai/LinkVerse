# LinkVerse MVP 阶段 4：支付链路执行设计

## 1. 目标与范围

阶段 4 在已完成普通交易的前提下，建立 Trade 与 Payment 两个独立数据边界之间的模拟支付闭环。目标是证明支付创建、回调验签、状态同步、超时关单、迟到支付退款和对账能够幂等收敛。

本阶段只实现一个 `local/test` Profile 可用的 HMAC Mock Provider，不接入真实资金渠道，不实现多渠道、部分退款、分账或用户主动退款。Payment 只写 `linkverse_mvp_payment`，Trade 只写 `linkverse_mvp_trade`，禁止跨 Schema 查询和事务。

## 2. 数据与状态

Payment 通过新的 Flyway 迁移创建以下表：

| 表 | 用途 | 核心约束 |
|---|---|---|
| `payment_intent` | 保存一单唯一支付意图 | `intent_no`、`order_no` 唯一；金额、币种、用户、商户快照不可由客户端修改 |
| `payment_callback_log` | 保存通过验签的通知摘要 | `(provider, notification_id)`、`(provider, provider_txn_no)` 唯一 |
| `payment_exception` | 记录迟到成功等异常 | 异常号唯一；关联 Intent |
| `refund_attempt` | 幂等退款及未知结果恢复 | `refund_request_no` 唯一 |
| `outbox_event` | 事务内保存支付事实事件 | `event_id` 唯一；支持抢占、重试与停车 |

Payment Intent 状态固定为 `PENDING/SUCCEEDED/CLOSED/REFUND_PENDING/REFUNDED`。Trade 订单状态固定为 `PENDING_PAYMENT/CLOSING/PAID/CLOSED`。状态更新必须包含前置状态条件并检查影响行数。

## 3. 接口与事件

### 3.1 用户接口

| 接口 | 行为 |
|---|---|
| `PUT /api/v1/orders/{orderNo}/payment-intent` | Trade 校验订单所有者、状态、金额和有效期后，以订单号作为幂等键调用 Payment |
| `GET /api/v1/payment-intents/{intentNo}` | Payment 按 JWT `sub` 校验所有者，返回支付及退款状态 |
| `POST /api/v1/mock-provider/payment-intents/{intentNo}/confirm` | 仅 `local/test` 可用；生成签名并进入同一回调处理路径 |
| `POST /api/v1/payments/callbacks/mock` | 仅接受满足 HMAC、时间戳、商户、订单、金额和币种校验的通知 |

### 3.2 内部接口

内部接口只接受 `aud=linkverse-payment`、`token_use=service`、`sub/client_id=linkverse-trade`、`scope=payment.internal` 的服务令牌。

| 接口 | 行为 |
|---|---|
| `POST /internal/v1/payment-intents` | 按订单号直接插入 Intent；唯一键冲突后读取并返回原结果 |
| `GET /internal/v1/payment-intents/by-order/{orderNo}` | 供 Trade 恢复和对账查询 |
| `PUT /internal/v1/payment-intents/{orderNo}/close` | 幂等关闭；不存在时插入完整 `CLOSED` 墓碑 |

### 3.3 事件

- `PaymentSucceeded`：Payment 事务内与 `SUCCEEDED` 同时写 Outbox；Trade 验证订单号、金额和币种后更新订单。
- `PaymentClosed`：用于唤醒同步响应丢失后的恢复；Trade 必须重新查询 Payment 当前状态。

RabbitMQ 采用至少一次投递。发布不确定时允许重发；Trade 用 `(consumer_name,event_id)` 唯一键去重，业务事务提交后才 ACK。

## 4. 执行步骤

1. 增加 Payment 迁移、MyBatis-Plus 仓储、领域状态和金额值对象；状态迁移和幂等写入使用显式条件 Mapper SQL。
2. 实现内部创建、查询和关闭接口，先以数据库唯一约束裁决并发。
3. 在 Trade 增加支付编排：只接受订单所有者且订单仍可支付，使用现有 `client_credentials` 获取短期令牌。
4. 实现 Mock Provider、原始字节 HMAC 校验和回调幂等处理；回调秘密只来自环境变量。
5. 在消息 Starter 中增加最小 Outbox 发布器；Payment 启用 Relay，Trade 启用支付事件消费者。
6. 增加过期订单扫描：先条件进入 `CLOSING`，再幂等关闭 Payment，最后根据权威支付状态进入 `PAID` 或 `CLOSED`。
7. 实现迟到成功的 `REFUND_PENDING`、固定退款请求号、结果查询和 `REFUNDED` 收敛。
8. 提供订单—支付—退款对账查询，不自动覆盖未知差异。

## 5. 异常与恢复

- 同步调用超时不能推断失败，只能使用原订单号和幂等键有限重试或查询。
- 签名错误、时间戳过期、商户/金额/币种不匹配不占用业务幂等键，不改变 Intent。
- `PAID` 订单不得转为 `CLOSED`；关闭后迟到的成功通知不得重开订单。
- Outbox 发布失败保留记录；回调处理成功必须在本地事务提交后响应 Provider。
- 退款超时进入 `UNKNOWN`，只能按相同退款请求号查询或重试，不能直接标记失败。

## 6. 测试与验收门禁

- 同一订单并发创建 100 次只产生一个 Intent。
- 同一合法回调重放 100 次只发生一次有效迁移；伪造签名和错误业务字段全部拒绝。
- 支付创建与关闭、支付成功与关单各并发 1000 轮，只出现合法终态且无 500。
- Payment 不具备 Trade Schema 权限，用户令牌不能调用内部接口。
- RabbitMQ 中断后 Outbox 恢复投递；重复事件不重复更新订单。
- 迟到成功进入退款流程，订单不重开，退款状态最终可查询和对账。
- 全量 Maven `clean verify` 通过后才允许提交本阶段。
