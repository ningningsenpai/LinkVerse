## 1. 阶段定义与执行目标

本文所称“阶段 3”特指 **MVP 第 6～8 日的普通交易正确性**，不是长期规划中的完整“交易链路阶段”。目标是在 `linkverse-trade` 内以 MySQL 本地事务完成最小可验证闭环：商品查询、单商品单数量立即购买、幂等建单、条件扣库存、订单快照、订单所有者查询和只读的过期候选扫描。

阶段完成时必须证明：

1. 同一买家、同一幂等键最多产生一个订单并且只扣一次库存；
2. 并发购买最后一件库存时恰好一个请求新建成功，库存始终不为负；
3. 订单、库存和订单项处于同一事务，任一步失败全部回滚；
4. 价格、币种、卖家及商品信息由服务端生成并形成不可变快照；
5. 普通下单不依赖 Redis 或 RabbitMQ 可用；
6. 全量构建不破坏阶段 1～2 已通过的 84 个测试基线。

## 2. 当前基线与范围边界

- 运行基线：JDK 21、Maven Wrapper 3.9.10、Spring Boot 3.5.15、MySQL 8.4.11；Trade Schema 为 `linkverse_mvp_trade`，服务端口为 `18082`。
- `linkverse-trade` 当前只有安全、服务令牌和空的 `V1__baseline.sql`；本阶段沿用现有 Spring JDBC/JdbcTemplate，不额外引入 ORM。
- 继续采用 `api / application / domain / infrastructure` 四层；事务位于 application 层，domain 不依赖 Spring、JDBC、Redis 或 MQ。
- 旧 Java/Python 快照只作只读参考，不复制旧实体，不连接旧库，不在原目录上改造。

本阶段明确不实现 Payment Intent、支付回调、关单、退款、对账、秒杀活动、Redis Lua、业务 MQ、Outbox Relay、购物车、多商品订单、优惠券、物流、管理端 CRUD、论坛、推荐、Elasticsearch、前端及 Swagger/API 测试文档。阶段 4 才处理 `CLOSING/PAID/CLOSED` 及 Payment；阶段 5 才处理秒杀专用库存和消息收敛。

## 4. 冻结业务不变量

| 编号 | 不变量 |
|---|---|
| P3-INV-01 | MySQL 是商品、库存和订单的唯一事实源；Redis、RabbitMQ 不进入普通下单必经路径。 |
| P3-INV-02 | 数量固定为 `1`；价格、币种、买家、卖家、状态、订单号均由服务端决定。金额使用 `DECIMAL(19,4)`/`BigDecimal`，禁止 `float/double`。 |
| P3-INV-03 | 买家 ID 只能来自已验签用户 JWT 的 `sub`；忽略或拒绝请求体及 `X-User-Id` 中的身份。卖家不能购买自己的商品。 |
| P3-INV-04 | 库存扣减必须使用 `available >= 1` 的单条条件更新，并检查受影响行数；任何时刻 `available >= 0`。 |
| P3-INV-05 | 新订单只写入 `PENDING_PAYMENT`。阶段 3 不写 `CLOSING`、`PAID` 或 `CLOSED`。 |
| P3-INV-06 | `(buyer_id, idempotency_key)` 唯一。同键同请求返回原订单；同键不同请求返回冲突，不产生副作用。 |
| P3-INV-07 | 商品被修改后，既有订单项中的标题、作者、卖家、价格和币种快照不变。 |
| P3-INV-08 | 只有订单买家可以查询订单；其他已登录用户统一返回 `404`，避免枚举订单。 |
| P3-INV-09 | 过期扫描只读出到期候选；不关单、不释放库存、不调用 Payment。 |

## 5. 数据设计与迁移

### 5.1 查询驱动的最小表

本阶段新增 `V2__create_trade_core_tables.sql`，只创建以下四张表。生产迁移只追加、不修改、不删除；若 V2 已在任一环境执行，修正必须使用 V3 及后续前向迁移。

| 表 | 必需字段 | 约束与索引 |
|---|---|---|
| `book_listing` | `id BIGINT AUTO_INCREMENT`、`seller_id BIGINT`、`title VARCHAR(200)`、`author VARCHAR(128)`、`description VARCHAR(2000) NULL`、`unit_price DECIMAL(19,4)`、`currency CHAR(3)`、`status VARCHAR(16)`、`version BIGINT DEFAULT 0`、`created_at/updated_at DATETIME(6)` | 除 `description` 外全部 `NOT NULL`；PK `id`；`unit_price > 0`；状态仅 `ON_SALE/OFF_SALE`。用户属于 Identity Schema，不建立跨 Schema 外键。 |
| `sku_stock` | `listing_id BIGINT`、`available INT`、`version BIGINT DEFAULT 0`、`updated_at DATETIME(6)` | 全部 `NOT NULL`；PK `listing_id`；同 Schema FK 指向商品并限制删除；`available >= 0`。一个商品只有一行库存事实。 |
| `trade_order` | `id BIGINT AUTO_INCREMENT`、`order_no CHAR(32)`、`buyer_id/seller_id BIGINT`、`idempotency_key VARCHAR(64)`、`request_fingerprint CHAR(64)`、`status VARCHAR(24)`、`total_amount DECIMAL(19,4)`、`currency CHAR(3)`、`expire_at DATETIME(6)`、`paid_at/closed_at DATETIME(6) NULL`、`version BIGINT DEFAULT 0`、`created_at/updated_at DATETIME(6)` | 仅 `paid_at/closed_at` 可空；UNIQUE `order_no`；UNIQUE `(buyer_id,idempotency_key)`；INDEX `(status,expire_at,id)`；金额大于 0；状态值域为 `PENDING_PAYMENT/CLOSING/PAID/CLOSED`，阶段 3 只写第一种。 |
| `order_item` | `id BIGINT AUTO_INCREMENT`、`order_id BIGINT`、`line_no SMALLINT`、`listing_id/seller_id BIGINT`、`listing_version BIGINT`、`listing_title VARCHAR(200)`、`listing_author VARCHAR(128)`、`unit_price/line_amount DECIMAL(19,4)`、`quantity INT`、`currency CHAR(3)`、`created_at DATETIME(6)` | 全部 `NOT NULL`；UNIQUE `(order_id,line_no)`；同 Schema FK 指向订单和商品；`quantity = 1`；金额大于 0。 |

四张表固定使用 InnoDB 和 `utf8mb4_0900_ai_ci`；技术键单列使用 ASCII 二进制排序规则。主键均自增，业务写入必须显式提供状态、金额、身份、版本以外的必填字段；`created_at/updated_at` 默认 `CURRENT_TIMESTAMP(6)`，更新操作显式刷新 `updated_at`。迁移和集成测试启用 MySQL 严格模式，并验证金额、币种大写三字母、状态值域、非零时间和非空约束。

`order_no` 使用 Java UUID 去除连字符后的 32 位值；`order_no`、`idempotency_key` 和 `request_fingerprint` 使用 ASCII 二进制排序规则，避免大小写折叠。时间统一按 UTC 写入，应用注入 `Clock`，JDBC 会话固定 UTC。当前接口只有按商品主键和订单号查询，不预建商品列表、买家列表或卖家列表索引；出现真实查询后再以执行计划补充。

`paid_at`、`closed_at` 和订单后续状态只为阶段 4 的前向兼容，不授权阶段 3 更新。`reservation_id`、`seckill_campaign`、`outbox_event` 和 `consumed_event` 本阶段不创建：没有消费者时不生产 `OrderCreated`，避免制造无法验收的消息链路。

MVP 中卖家账户同时代表收款商户，`trade_order.seller_id` 就是不可变的商户快照。阶段 4 创建 Payment Intent 时将其映射为 Payment 请求中的 `merchant_id`；本阶段不另建商户表，也不允许客户端提交商户标识。

## 6. 接口与幂等契约

| 接口 | 请求 | 成功语义 | 主要失败 |
|---|---|---|---|
| `GET /api/v1/listings/{listingId}` | 用户 JWT | `200` 返回服务端商品与可售库存 | 不存在 `404` |
| `POST /api/v1/orders` | 用户 JWT；Header `Idempotency-Key`；Body 仅 `listing_id`、`quantity=1` | 新建 `201`；同请求重放 `200`，返回相同 `order_no` | 参数 `400`；不可售、自购、库存不足或幂等冲突 `409` |
| `GET /api/v1/orders/{orderNo}` | 用户 JWT | 所有者 `200`，返回订单与快照 | 不存在或非所有者统一 `404` |

`Idempotency-Key` 必须为 8～64 个可见 ASCII 字符。应用计算 `SHA-256("v1|buyer_id|listing_id|quantity")` 作为 `request_fingerprint`；键随订单长期保存，不设 TTL。同一买家同键且摘要一致时返回原订单，摘要不一致返回 `TRADE_IDEMPOTENCY_KEY_REUSED`，不同买家可独立复用同一键。

商品响应固定包含 `listing_id/seller_id/title/author/description/unit_price/currency/status/available/updated_at`；下单响应包含 `order_no/status/total_amount/currency/expire_at`；订单详情在此基础上包含一个 `item` 快照。金额以保留四位小数的 JSON 字符串返回，例如 `"12.3400"`；时间以 UTC ISO-8601 字符串返回，最多保留六位小数。POST 中商品不存在返回 `TRADE_LISTING_NOT_FOUND/404`。

错误响应沿用阶段 2 的中文 Problem Details，至少固定：`TRADE_LISTING_NOT_FOUND`、`TRADE_LISTING_NOT_ON_SALE`、`TRADE_SELF_PURCHASE_NOT_ALLOWED`、`TRADE_OUT_OF_STOCK`、`TRADE_IDEMPOTENCY_KEY_REQUIRED`、`TRADE_IDEMPOTENCY_KEY_INVALID`、`TRADE_IDEMPOTENCY_KEY_REUSED`、`TRADE_ORDER_NOT_FOUND`。不得返回 SQL、堆栈、内部地址或敏感头。

## 7. 核心事务算法

幂等冲突处理必须位于事务外层，业务写入位于一个 `@Transactional` 执行器内：

1. 外层从 JWT 取得 `buyer_id`，校验参数并计算请求摘要；
2. 外层先按 `(buyer_id,idempotency_key)` 做**只读快速查询**：已存在且摘要相同则立即重放，摘要不同则立即 `409`。该查询只保证语义正确，不承担并发互斥；因此商品后来下架也不影响原请求重放；
3. 未命中时进入事务，读取商品，校验 `ON_SALE` 且卖家不是买家，以当前数据生成金额、快照和 `expire_at`；
4. **直接插入订单**，让 `(buyer_id,idempotency_key)` 唯一键裁决并发未命中的重复请求，禁止以步骤 2 的查询代替唯一约束；
5. 执行条件扣减：`UPDATE sku_stock SET available=available-1, version=version+1, updated_at=? WHERE listing_id=? AND available>=1`；受影响行数不是 1 则抛出库存不足；
6. 写入一条 `order_item` 快照并提交；订单默认 15 分钟过期，配置键为 `linkverse.trade.order-payment-timeout=15m`；
7. 若订单唯一键冲突，让原事务完整回滚，再由外层按买家和幂等键读取已提交订单；摘要相同则重放，摘要不同则返回 `409`。只有确实查到该幂等记录时才按重放处理；极低概率的 `order_no` 冲突重新生成订单号并限次重试。

该顺序保证相同幂等键并发不会重复扣库存；库存不足或订单项失败会连同刚插入的订单一起回滚。不同幂等键争抢库存 1 时，条件更新保证仅一个事务成功。

过期框架只实现 `findDuePending(now, afterExpireAt, afterId, limit)`：固定本轮截止时间 `now`，查询 `status='PENDING_PAYMENT' AND expire_at<=now`，以 `(expire_at,id)` 作 Keyset 游标并升序限制批量；首批游标为空。它可以被集成测试或后续调度器调用，但阶段 3 不启用修改状态的定时任务。

## 11. 完成定义、回滚与阶段 4 入口

阶段 3 只有在 D6、D7、D8 门禁全部满足，且 `08-MVP阶段3验收记录.md` 保存实际命令、环境版本、测试数量、黑盒响应摘要，以及 Luna 查阅/测试任务所用模型和 `max` 推理档位后才算完成。测试数量以最终运行输出为准，不预设新增数量。

代码缺陷通过小提交回滚；数据库迁移一旦执行不得删除或改写 V2，只能追加前向修复。不得删除业务数据或旧快照。若唯一键语义、金额精度、事务回滚、并发库存或基础设施独立性任一失败，立即停止进入阶段 4。

阶段 4 的输入仅包括：稳定的订单号、买家、作为商户快照的 `seller_id`、不可变金额/币种、`PENDING_PAYMENT` 状态、`expire_at` 和只读候选查询。Payment Intent、`CLOSING` 认领、支付事件消费、终态转换及库存释放必须在阶段 4 另行设计和验收。

## 12. 主要风险与控制

| 风险 | 控制措施 |
|---|---|
| MySQL 默认隔离级别下并发超卖 | 不依赖先查库存；以条件更新和受影响行数作为唯一扣减结果。 |
| 重复请求在唯一键等待后产生重复副作用 | 先插订单；唯一键异常退出并回滚事务，再在事务外读取原结果。 |
| 文档长期方案与 MVP 当前实现混用 | 本阶段以实际 JdbcTemplate 基线和本文冻结边界为准；MyBatis-Plus 属长期选型，不在阶段中途迁移。 |
| 演示数据污染生产 | local/test 独立 Flyway location；默认 Profile 不加载种子。 |
| 过早引入 MQ、缓存或支付状态 | 阶段 3 无业务消息和缓存依赖，过期扫描只读；后续按阶段增加。 |
| 测试为通过而放宽约束 | Luna 负责测试与查阅，当前主模型负责业务裁决；任何语义调整必须先更新本文并说明理由。 |
