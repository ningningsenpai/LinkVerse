# 2026-09-06 推荐系统训练测试执行总结

状态：本轮计划执行及汇总完成。工程链路通过本地验收；排序质量与全量 HTTP 延迟未满足晋级条件，模型保持 `ENGINEERING` 用途。

## 已确认的结论

本轮已经执行旧模型复评、5+5 冒烟、30+50 正式搜索、真实 HTTP 反馈与快照重训，并据测试结果修复数据、服务和测量工具。**目前没有可靠证据证明排序质量提升，因此不晋级算法模型。** 本地真实业务模型只作为 `ENGINEERING` 用途使用。

正式搜索耗时约 53.8 分钟，保存了 30 次双塔搜索、50 次精排搜索、864 条 epoch 记录和 641 次资源采样。固定三个随机种子完成重训，同种子重复的最大权重差为 0。训练工作集采样峰值约 4.38 GiB，PyTorch 已分配显存峰值约 437 MiB；整卡显存还包含其他图形进程，不能与训练分配量混为一谈。

## 推荐效果

正式回归冻结了相同时间边界、目录和公共历史排除口径，测试窗口有 7,581 个用户，其中 7,541 个具备可评估目标。以下是最终列表的回归指标，不能当作自然用户 CTR、转化率或收入收益。

| 指标 | 正式反馈前 | 正式反馈后 |
|---|---:|---:|
| NDCG@20 | 0.003242 | 0.003299 |
| Recall@50 | 0.034151 | 0.038271 |
| HitRate@20 | 0.014189 | 0.014454 |
| 目录覆盖率@20 | 76.88% | 74.88% |
| 类目配额违规 | 0 | 0 |
| Top20 短列表 | 0 | 0 |

NDCG 配对差值为 0.0000573，95% bootstrap 区间为 **[-0.0008334，0.0009791]**，跨过零。召回率提高不等于最终排序已经改善。此窗口此前已经查看，所有区间都属于探索性历史回归。

进一步固定反馈前的人群成员，稀疏用户 NDCG 为 0.002646 → 0.005154（763 个有效用户），活跃用户为 0.003314 → 0.003095（6,768 个有效用户）。冷启动只有 10 人，Top20 两轮均未命中目标，不能据此评价冷启动质量。原始分群按各模型词表定义，反馈后有 5 人从冷启动变为已知用户，因此跨版本比较采用另存的固定分群表，避免混淆成员变化。

旧模型的公共历史过滤后 NDCG 从 0.007866 到 0.010494，但其最终补位路径存在大面积配额违规，不能直接把这些高分当作满足业务约束后的效果。新冒烟模型也没有可靠提升：NDCG 从 0.006118 到 0.006019，配对区间跨零。冒烟评估器曾在重排后再次移除历史，造成反馈前 31 个配额违规；评估器已改为在最终重排前传入公共排除集合。

### 消融发现

消融只比较冻结混合候选池中的处理步骤，不恢复上游已经裁掉的对象，也不构成端到端召回渠道消融。

| 固定候选池诊断 | NDCG@20 |
|---|---:|
| 保留精排、MMR 和业务配额 | 0.003429 |
| 不使用精排，按原召回分数重排 | 0.006696 |
| 不使用 MMR 相似度惩罚，保留业务配额与新品约束 | 0.004313 |
| 去除仅由 ItemCF 提供的对象 | 0.003345 |
| 训练时热门排序加业务配额基线 | 0.002741 |

固定候选池缺失造成 5 个短列表，已经计入分母。完整在线模型会补充候选，因此这里的池内参考分数与完整在线结果并不相同。

这些结果把下一轮重点指向精排和重排的衔接。当前精排只有五个历史特征，没有直接使用双塔、ItemCF、内容召回等相关性分数；训练组为一个正例加最多四个负例，与线上数百候选的难度差异很大。正式精排最终只有一棵树，叶分数约在 -0.0211～0.0314；直接与余弦相似度放入 MMR，可能让多样性惩罚压过相关性差异。这些是待验证的解释，未据此使用测试集挑选新参数。

另一个已经修复的问题是同分偏差：旧训练组将正例固定放在第一位，旧分组 NDCG 对同分保留原顺序，可能高估验证结果并影响早停。现已使用同分排列的期望增益，并确定性打乱训练组顺序；LightGBM 早停与搜索使用同一修正指标。五个对象完全同分时，单正例的 NDCG@20 约为 0.5897，不会因正例原始位置而得到 1.0。**30+50 正式模型的精排选参发生在此修正之前，需要在后续正式迭代中重新搜索；本轮未将其晋级。**

## 真实反馈与数据修复

使用本轮独立编号的 20 个账号、120 个商品夹具，经 Gateway、Trade、Identity、Payment 和 Recommendation 执行本地真实 HTTP 请求。支付提供方为本地 Mock。

- 执行 5 个用户 × HOME、DETAIL、CART 三个场景，核对曝光、详情、购物车、下单、支付和终态。
- 确定性覆盖重复下单、重复支付、一次主动退款和一次迟到支付运营补偿。
- 从 API 返回的推荐投递 ID 建立归因，不把订单和会话记录重复计为多个偏好样本。
- 修复 delivery 字段导出和只读一致性快照事务；来源标记为 `REAL + SCRIPTED`，与自然流量区分。
- 最新已审计快照有 767 条事件，归因为 355 个样本，包含 323 个成熟曝光负样本、2 个主动退款负样本，投递 ID 无缺失。
- 按预先约定的会话阶段冻结窗口，样本数为 340 / 5 / 5 / 5。此样本量足以检查工程闭环，不足以证明自然用户收益。

标签成熟以快照时间为界，保留 30 分钟曝光成熟规则。训练与评估使用同一快照 `exported_at`；跨窗口归因链和延迟标签会被剔除或拒绝。训练历史按标签真正可用的时间推进，未来退款不会改写过去的训练样本，负采样只使用当时已经发布的商品。

修正同分指标后的最后一次小样本重训耗时 10.2 秒，保存 5+5 次搜索、46 条 epoch 和同种子复现记录。其精排只有一个取值为 0 的叶子，验证分数 0.5897 等于五对象同分基准；5 个测试用户的 Top20 两轮均未命中、Recall@50 均为 0.4。这再次说明该包适合检查工程功能，不能作为排序质量候选。355 个归因样本也不等于 355 个训练正例，扩大真实候选组和正反馈样本是后续必要工作。

## 测量中发现的问题

第一轮进程内基准在每次推断计时结束后写磁盘日志，可能形成隐藏的思考时间。该轮已标记不用于验收；复跑改为批次结束后记录原始结果，并报告吞吐和实际平均并发度。

本机 HTTPX 默认读取系统代理，最初连 `127.0.0.1` 的请求也走代理。这些运行已经保留并标注路径；直连复测显式使用 `trust_env=False`。代理路径和直连结果分别报告。

完整模型与业务夹具分别验收。全量模型有 6,262 个商品，日常 100 候选与压力 300 候选单列；真实业务夹具只有 120 个商品，不能用其速度冒充全量服务能力。单、双工作进程也分别记录内存和运行配置。双进程的服务端 `/metrics` 是各进程独立计数，本轮使用外部逐请求记录和容器总资源统计，不能把随机一个进程的计数当作总量。

基线长稳曾提前结束，以便让完整 30 分钟验收覆盖最终工程代码；该次数据保留并标注未完成，不作为长稳通过证据。最终版本另开运行，完整完成长稳、独立复跑、故障及分层性能测试。

优化后的全量进程内推断三轮各 2,000 次请求，实际平均并发约 19.9，p95 为 175.0 / 174.8 / 163.3ms，成功率 100%，满足进程内 300ms 门槛。吞吐约 167～178 次/秒；p99 仍有尾延迟，不能只报告 p95。

全量单进程直连 HTTP 的 300 候选、20 并发 p95 从基线 442.5ms 降至优化版 386.9ms；优化版日常 100 候选为 318.9ms，仍未达到本轮在 HTTP 工具中采用的 300ms 验收线。ADR 的原始 300ms 指进程内推断，这里的 HTTP 验收更严格，两者分别报告。双进程的两档 p95 为 341.4 / 338.8ms，并有 7 次连接中断，日志记录子进程重启，未采用。随后调整工作进程健康等待参数时，当前镜像的 Uvicorn 不支持该参数，容器未进入采样；这是单独保留的启动配置失败，不能归因于模型加载超时。按计划停止 30/50 并发扩容，不反复追加配置寻找一次通过。

本轮分层压测使用 Python HTTPX 实现，代替原计划拟新增的 k6 场景；保存每个请求、明确预热窗口、分群分母、吞吐与直连策略。Gateway 也暂按 800ms 作为本地工具的保守验收值，原 ADR 的 800ms 指 Trade 层，报告中分别列出两层。

### 故障、安全与换版

真实 HTTP 的优化等价性验证为 45/45。用户令牌、错误受众、畸形令牌和伪造签名的服务请求均返回 401。坏包的 100 次请求和越界指针的 20 次请求保持旧模型服务；两次并发换版分别约 0.515 和 1.031 秒生效。

暂停容器时的 30 并发请求都得到完整数据库降级；Java 记录了 10 次并发容量拒绝和 20 次超时，证明信号量路径被实际覆盖。暂停/停止各 10 次业务请求完整降级。无活动模型时 liveness 为 200、readiness 和 Python 推荐为 503，Gateway 完整降级。

暂停、停止和无模型恢复约为 29.813 / 29.422 / 30.500 秒，包含熔断等待；无模型恢复比 30 秒略长，不能写成所有故障都严格在 30 秒内恢复。旧模型指针回滚及实际版本核对在约 1 秒内完成，测试最终恢复活动工程版本。

最终 Python 回归 41 项通过；Trade 与共享模块回归 66 项通过，新增遥测及内部 HTTP 合同针对测试 5 项通过。最后的只读采集和汇总工具另做语法检查并实际执行。完整日志保留在证据目录，未执行全仓 `clean verify`。

### 长稳与独立复跑

30 分钟长稳和 5 分钟独立复跑均完整完成。负载固定为 20 虚拟用户、每轮 1 秒思考时间。长稳采样得到 33,998 次请求，成功率和有效模型率均为 100%，降级为 0，p95 / p99 为 85.1 / 114.1ms，吞吐 18.89 次/秒。已知用户 8,497 次、冷启动 25,501 次请求均通过分群门禁。

长稳保存 366 次完整资源采样和 62 次可用队列采样，所有队列的 ready、unacknowledged 和总积压峰值均为 0。推荐容器前后五分钟内存中位数均为 157.1MiB，采样峰值 170.4MiB，后段斜率约 0.0023MiB/分钟；MySQL 中位数约从 710.9 增至 723.0MiB。Java 工作集后半段有回落，不把操作系统工作集回落等同于已经排除堆泄漏。主机 CPU 中位数约 24.5%、p95 约 33.9%，其他图形和用户应用保持运行。

20 个账号在开始、约第 14 分钟、第 28 分钟分别完成登录更新，共 60 条成功记录，更新期间没有推荐鉴权错误。这里记录的是客户端重新登录获得令牌，不是 OAuth 刷新令牌授权模式。

独立复跑采样得到 5,674 次请求，已知用户 1,419 次、冷启动 4,255 次，均为 100% 有效模型响应、零降级。p95 / p99 为 88.9 / 115.4ms，吞吐 18.91 次/秒，保存 67 次完整资源和 13 次可用队列采样，队列积压仍为 0。最终业务矩阵、长稳和复跑合计 **106,114 次**正常请求全部返回预期模型；Java 降级累计计数在故障验证结束后保持 217，结束时连接池 active、pending 均为 0。

这证明当前小目录工程链路在所测负载下可运行，不证明自然转化收益，也不能替代全量目录和更长时间的容量验收。5 分钟复跑的前后五分钟窗口会重叠，不用两个中位数相等来证明无泄漏。

1. **冻结新的数据与验证窗口。** 保留本轮快照和测试窗口作为回归集，新增未查看窗口用于确认；记录来源、成熟率、缺失率、跨窗剔除和每组有效分母。
2. **修正精排训练任务。** 使用已修正的同分指标重新进行正式搜索；用曝光候选组或离线真实召回候选构建训练组，增加可验证的难负例，减少与线上难度不一致的随机小组。
3. **补充相关性特征并校准重排。** 在验证集上比较召回分数、渠道排名、用户负反馈等特征，并检查精排分数尺度与 MMR 的关系；参数选择不得使用本轮已查看测试得分。
4. **控制模型包和训练开销。** 将每用户大规模 JSON 候选逐步转换为紧凑数组、偏移和来源编码；剖析样本构造及重复目录处理，缓存与数据哈希、切分和特征版本绑定的中间结果。
5. **重复完整工程链路。** 每个新候选执行快照审计、三种子重训、同种子复现、全量与分群评估、确定性支付和退款闭环，以及真实 API 版本核对。
6. **按资源规格验收运行。** 固定工作进程数、候选数、夹具、场景比例、思考时间和代理策略；分开核算已知/冷启动模型有效率、降级率、p95/p99、内存及恢复时间。多进程发布前补齐指标聚合和大包换版验证。Java 当前在同一事务内逐项写入 20 条投递记录，后续可在保留投递 ID 对应关系与原子性的前提下验证批量写入；新阶段计数可用于判断实际改善。
7. **按证据决定晋级。** 离线质量、数据隔离、测试、真实 HTTP、延迟与回滚全部通过才进入回归候选；自然流量候选还需要独立确认性证据。未通过时保留当前工程版本和旧包，记录失败，不覆盖历史结果。
